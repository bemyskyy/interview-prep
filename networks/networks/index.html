    Сети и протоколы¶

    Модель OSI и TCP/IP — быстрый контекст¶

    На собесе редко спрашивают все 7 уровней OSI наизусть, но нужно понимать где живут протоколы которые ты используешь каждый день.

    OSI (7 уровней)          TCP/IP (4 уровня)     Протоколы

7. Прикладной            Прикладной            HTTP, HTTPS, WebSocket,
6. Представления    →                          gRPC, DNS, SMTP, FTP
5. Сеансовый

4. Транспортный          Транспортный          TCP, UDP

3. Сетевой               Сетевой               IP, ICMP (ping)

2. Канальный             Канала доступа        Ethernet, Wi-Fi, MAC
1. Физический

    На практике ты работаешь с уровнями 4 (TCP/UDP) и выше. Уровни 1-3 — зона DevOps/сетевых инженеров.

    TCP vs UDP¶

    TCP (Transmission Control Protocol)¶

    Надёжная, упорядоченная, с контролем потока. Соединение устанавливается перед передачей данных.

    Трёхстороннее рукопожатие (Three-Way Handshake):

    Клиент                          Сервер
   |  ──── SYN ──────────────→  |   "Хочу соединиться, мой seq=100"
   |  ←─── SYN-ACK ──────────  |   "Ок, жди seq=200, подтверждаю твой 101"
   |  ──── ACK ──────────────→  |   "Подтверждаю твой 201"
   |                            |
   | ←── Данные передаются ──→  |   Соединение установлено

    Четырёхстороннее закрытие (Four-Way Teardown):

    Клиент ──── FIN ────→ Сервер   "Я отправил всё"
Клиент ←─── ACK ──── Сервер   "Получил, но у меня ещё есть данные"
Клиент ←─── FIN ──── Сервер   "Теперь и я закончил"
Клиент ──── ACK ────→ Сервер   "Принято"

    Гарантии TCP: - Доставка (потерянные пакеты пересылаются) - Порядок (пакеты собираются в правильном порядке) - Целостность (checksum на каждый сегмент) - Контроль перегрузки (не заливает канал)

    Когда использовать: HTTP/HTTPS, базы данных, email, передача файлов — везде где важна надёжность.

    UDP (User Datagram Protocol)¶

    Без соединения, без гарантий, максимальная скорость. Отправил и забыл.

    Клиент ──── Датаграмма ────→ Сервер
            (может потеряться, прийти не в том порядке, задублироваться)

    Что UDP не делает: не устанавливает соединение, не подтверждает доставку, не контролирует порядок, не переотправляет потери.

    Когда использовать: - Видеозвонки, стриминг (лучше пропустить кадр, чем ждать) - Online-игры (старый пакет с позицией игрока не нужен) - DNS (один маленький запрос, быстро) - QUIC / HTTP/3 (UDP с надёжностью реализованной поверх)

    Сравнение¶

    TCP UDP
    Соединение Да (рукопожатие) Нет
    Гарантия доставки Да Нет
    Порядок пакетов Гарантирован Не гарантирован
    Скорость Медленнее (overhead) Быстрее
    Применение HTTP, БД, файлы DNS, видео, игры, QUIC

    Вопрос на собесе

    "Можно ли сделать надёжную передачу поверх UDP?"

    Да — именно так работает QUIC (HTTP/3). Реализует надёжность и порядок на уровне приложения, но без overhead TCP-рукопожатия. Устанавливает соединение быстрее и лучше работает при потерях пакетов.

    HTTP — главный протокол веба¶

    Эволюция версий¶

    HTTP/1.0 — одно соединение на один запрос. Открыл → запросил → закрыл. Дорого.

    HTTP/1.1 — Keep-Alive: одно TCP-соединение для нескольких запросов. Но запросы строго последовательны — Head-of-Line Blocking: пока первый запрос не ответил, второй ждёт.

    HTTP/2 — бинарный протокол, мультиплексирование: несколько запросов параллельно в одном TCP-соединении. Header Compression (HPACK). Server Push (сервер отправляет ресурсы без запроса). Но Head-of-Line Blocking остался на уровне TCP (потеря одного пакета блокирует все потоки).

    HTTP/3 (QUIC) — поверх UDP. Мультиплексирование без блокировки: потеря пакета в одном потоке не влияет на другие. Быстрое установление соединения (0-RTT для повторных соединений). TLS 1.3 встроен.

    HTTP-запрос под капотом¶

    GET /api/habits/1 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGci...
Content-Type: application/json
Accept: application/json
User-Agent: Java-HttpClient/11

(тело запроса — для POST/PUT/PATCH)

    HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 127
Cache-Control: max-age=3600
X-Request-Id: abc-123

{"id": 1, "name": "Бег", "status": "ACTIVE"}

    Коды статусов¶

    1xx — Информационные
  100 Continue — продолжай отправлять тело

2xx — Успех
  200 OK             — стандартный успех
  201 Created        — ресурс создан (POST)
  204 No Content     — успех, тела нет (DELETE, PUT без тела)

3xx — Перенаправление
  301 Moved Permanently  — постоянный редирект (обновить ссылки)
  302 Found              — временный редирект
  304 Not Modified       — кэш актуален, тело не возвращается

4xx — Ошибка клиента
  400 Bad Request        — невалидные данные
  401 Unauthorized       — не аутентифицирован (нет/плохой токен)
  403 Forbidden          — аутентифицирован, но нет прав
  404 Not Found          — ресурс не найден
  405 Method Not Allowed — метод не поддерживается
  409 Conflict           — конфликт (например, дубликат)
  422 Unprocessable      — валидация прошла, но семантика неверна
  429 Too Many Requests  — rate limiting

5xx — Ошибка сервера
  500 Internal Server Error  — неожиданная ошибка
  502 Bad Gateway            — upstream вернул плохой ответ
  503 Service Unavailable    — сервис перегружен или на обслуживании
  504 Gateway Timeout        — upstream не ответил вовремя

    401 vs 403 — частая путаница

    401 — "Кто ты? Авторизуйся." (нет токена или токен невалиден) 403 — "Я знаю кто ты, но тебе сюда нельзя." (прав недостаточно)

    HTTP-методы и идемпотентность¶

    Метод Идемпотентен Безопасен Применение
    GET ✅ Да ✅ Да Получить ресурс
    POST ❌ Нет ❌ Нет Создать ресурс
    PUT ✅ Да ❌ Нет Полная замена ресурса
    PATCH ❌ Нет* ❌ Нет Частичное обновление
    DELETE ✅ Да ❌ Нет Удалить ресурс
    HEAD ✅ Да ✅ Да Как GET, но без тела
    OPTIONS ✅ Да ✅ Да CORS preflight, узнать методы

    Идемпотентен — повторный вызов с теми же данными даёт тот же результат. Безопасен — не изменяет состояние сервера.

    *PATCH может быть идемпотентным, если операция абсолютная ("set name=X"), и не идемпотентным, если относительная ("increment counter").

    HTTPS и TLS¶

    Что такое TLS¶

    TLS (Transport Layer Security) — криптографический протокол поверх TCP. Обеспечивает: - Конфиденциальность — данные зашифрованы, перехватчик видит только шум - Целостность — данные не изменены в пути (MAC/HMAC) - Аутентификация — сертификат подтверждает личность сервера

    TLS Handshake (упрощённо, TLS 1.2)¶

    Клиент                                    Сервер
  │                                          │
  │──── ClientHello ───────────────────────→ │
  │     (версии TLS, случайное число,         │
  │      список поддерживаемых шифров)        │
  │                                          │
  │ ←── ServerHello ──────────────────────── │
  │     (выбранный шифр, случайное число,     │
  │      сертификат с публичным ключом)       │
  │                                          │
  │     Клиент проверяет сертификат           │
  │     (подписан доверенным CA?)             │
  │                                          │
  │──── Pre-master secret ─────────────────→ │
  │     (зашифровано публичным ключом)        │
  │                                          │
  │     Обе стороны генерируют               │
  │     симметричный ключ сессии              │
  │                                          │
  │──── Finished (зашифровано) ────────────→ │
  │ ←── Finished (зашифровано) ──────────── │
  │                                          │
  │ ←────── Данные зашифрованы ──────────── │

    TLS 1.3 упрощает хэндшейк до 1 round-trip (вместо 2 в TLS 1.2), убирает устаревшие алгоритмы, поддерживает 0-RTT для повторных соединений.

    Сертификаты и PKI¶

    Root CA (Корневой центр сертификации)
  └── Intermediate CA
        └── Сертификат example.com
              ├── Публичный ключ
              ├── Домен (Subject)
              ├── Срок действия
              └── Подпись Intermediate CA

    Браузер доверяет Root CA (встроен в ОС). Проверяет цепочку подписей снизу вверх. Если цепочка валидна и домен совпадает — соединение доверенное.

    Вопрос на собесе

    "Что происходит при HTTPS-запросе, прежде чем придут данные?"

    DNS-резолюция → TCP-рукопожатие (3 пакета) → TLS-хэндшейк (2 round-trips для TLS 1.2, 1 для TLS 1.3) → HTTP-запрос. Итого: до первого байта данных — 3-5 round-trips. Именно поэтому HTTP/2 и Keep-Alive так важны.

    REST vs gRPC¶

    REST (Representational State Transfer)¶

    REST — архитектурный стиль, не протокол. Работает поверх HTTP.

    Принципы REST:

    1. Stateless — каждый запрос самодостаточен, сервер не хранит состояние клиента
    2. Uniform Interface — ресурсы идентифицируются URL, операции — HTTP-методами
    3. Client-Server — чёткое разделение ответственности
    4. Cacheable — ответы могут кэшироваться
    5. Layered System — клиент не знает, есть ли между ним и сервером прокси/балансировщики

    Правильный REST API:

    # Ресурсы — существительные, не глаголы
GET    /api/habits          → список привычек
GET    /api/habits/1        → конкретная привычка
POST   /api/habits          → создать привычку
PUT    /api/habits/1        → полная замена
PATCH  /api/habits/1        → частичное обновление
DELETE /api/habits/1        → удалить

# Вложенные ресурсы
GET    /api/users/42/habits      → привычки конкретного пользователя
POST   /api/users/42/habits      → создать привычку для пользователя

# Фильтрация, сортировка, пагинация — query params
GET    /api/habits?status=ACTIVE&sort=createdAt&page=0&size=20

# Версионирование
/api/v1/habits
/api/v2/habits

    Что НЕ является REST (хотя часто называется):

    POST /api/getHabits          ← глагол в URL — RPC-стиль, не REST
GET  /api/habits/delete/1    ← действие в URL
GET  /api/habits?action=create ← действие в параметре

    gRPC (Google Remote Procedure Call)¶

    gRPC — фреймворк RPC от Google. Работает поверх HTTP/2, использует Protocol Buffers (protobuf) для сериализации.

    Контракт через .proto файл:

    syntax = "proto3";

package habits;

service HabitService {
  rpc GetHabit (GetHabitRequest) returns (HabitResponse);
  rpc CreateHabit (CreateHabitRequest) returns (HabitResponse);
  rpc StreamHabits (StreamRequest) returns (stream HabitResponse); // серверный стриминг
  rpc SyncHabits (stream HabitUpdate) returns (stream HabitResponse); // двусторонний стрим
}

message GetHabitRequest {
  int64 id = 1;
}

message HabitResponse {
  int64 id = 1;
  string name = 2;
  string status = 3;
  int64 created_at = 4;
}

    Из .proto генерируется клиентский и серверный код на любом языке (Java, Go, Python, Kotlin...).

    gRPC в Spring Boot:

    // Server
@GrpcService
public class HabitGrpcService extends HabitServiceGrpc.HabitServiceImplBase {

    @Override
    public void getHabit(GetHabitRequest request,
                         StreamObserver<HabitResponse> responseObserver) {
        HabitDto habit = habitService.findById(request.getId());

        HabitResponse response = HabitResponse.newBuilder()
            .setId(habit.getId())
            .setName(habit.getName())
            .setStatus(habit.getStatus().name())
            .build();

        responseObserver.onNext(response);
        responseObserver.onCompleted();
    }
}

    REST vs gRPC — сравнение¶

    REST gRPC
    Протокол HTTP/1.1 или HTTP/2 HTTP/2 обязательно
    Формат данных JSON (текст, читаемо) Protobuf (бинарный, компактно)
    Контракт OpenAPI/Swagger (опционально) .proto (обязательно)
    Типизация Слабая Строгая (генерация кода)
    Производительность Медленнее (JSON parsing) В 5-10x быстрее (бинарный)
    Стриминг SSE, WebSocket (отдельно) Встроен (4 режима)
    Браузер Нативно Нужен grpc-web прокси
    Читаемость Легко дебажить (curl, Postman) Нужны специальные инструменты
    Когда Публичное API, браузер, простота Внутренние микросервисы, производительность, стриминг

    Когда что выбирать

    REST — публичное API (клиенты разные: браузер, мобилка, сторонние), команда привычна к JSON, нужна простота дебага.

    gRPC — внутренние микросервисы между собой, высокие требования к производительности, стриминг данных в реальном времени, строгий контракт между командами.

    WebSocket¶

    HTTP — однонаправленный (клиент запрашивает, сервер отвечает). Для двустороннего реального времени есть WebSocket.

    Клиент                              Сервер
  │──── HTTP Upgrade Request ──────→ │   "Переключись на WebSocket"
  │ ←── 101 Switching Protocols ──── │   "Ок"
  │                                  │
  │ ←──── Сообщение ──────────────── │   Полнодуплексная связь
  │──── Сообщение ─────────────────→ │   любая сторона может писать
  │ ←──── Сообщение ──────────────── │   в любой момент

    Spring WebSocket:

    @Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {

    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(habitUpdateHandler(), "/ws/habits")
            .setAllowedOrigins("*");
    }
}

// Или STOMP поверх WebSocket (более высокоуровневый)
@MessageMapping("/habits/update")
@SendTo("/topic/habits")
public HabitDto updateHabit(HabitUpdateDto dto) {
    return habitService.update(dto);
    // Все подписчики /topic/habits получат обновление
}

    Когда WebSocket: чаты, коллаборативное редактирование, live-уведомления, трейдинговые терминалы, онлайн-игры.

    Server-Sent Events (SSE) — более простая альтернатива для одностороннего потока сервер → клиент:

    @GetMapping(value = "/api/habits/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<HabitDto> streamHabits() {
    return habitService.streamUpdates(); // WebFlux
}

    DNS — как имя превращается в IP¶

    Браузер вводишь: api.example.com

1. Проверяем кэш браузера → не нашли
2. Проверяем кэш ОС (/etc/hosts) → не нашли
3. Запрос к Recursive Resolver (твой провайдер или 8.8.8.8)
4. Resolver → Root Nameserver: "Кто знает про .com?"
5. Resolver → TLD Nameserver (.com): "Кто знает про example.com?"
6. Resolver → Authoritative Nameserver example.com: "Какой IP у api.example.com?"
7. Получаем A-запись: 93.184.216.34
8. Кэшируем с TTL (time to live)

    Типы DNS-записей:

    A        → IPv4 адрес              api.example.com → 93.184.216.34
AAAA     → IPv6 адрес
CNAME    → Псевдоним               www → example.com
MX       → Почтовый сервер        example.com → mail.example.com
TXT      → Текст                   SPF, DKIM, верификация домена
NS       → Nameserver              Где лежат записи домена
SRV      → Сервис + порт          Используется в gRPC, Kubernetes

    Вопрос на собесе

    "Что происходит при первом запросе к новому микросервису?"

    DNS-резолюция (может занять десятки ms если нет кэша) → TCP-хэндшейк → TLS-хэндшейк → HTTP-запрос. Именно поэтому в микросервисах критично: DNS-кэширование на стороне клиента, connection pooling (не создавать соединение на каждый запрос), Keep-Alive.

    Итоговая шпаргалка¶

    Тема Запомнить
    TCP vs UDP TCP: надёжно, медленно. UDP: быстро, ненадёжно. QUIC = UDP + надёжность
    TCP Handshake SYN → SYN-ACK → ACK. 3 пакета до начала передачи
    HTTP/1.1 vs HTTP/2 H2: бинарный, мультиплексирование, header compression, одно TCP
    HTTP/3 Поверх UDP (QUIC), нет HoL-блокировки на уровне транспорта
    401 vs 403 401 = не аутентифицирован. 403 = аутентифицирован, но нет прав
    Идемпотентность GET, PUT, DELETE — идемпотентны. POST — нет
    TLS Handshake Обмен сертификатом, согласование ключа, симметричное шифрование
    REST принципы Stateless, Uniform Interface (URL+методы), Cacheable
    REST ошибки Глаголы в URL, действия в параметрах, игнорирование HTTP-методов
    gRPC vs REST gRPC: бинарный, быстрый, стриминг, внутренние сервисы. REST: публичное API
    WebSocket Двусторонняя связь поверх HTTP (Upgrade). Для чатов, real-time
    SSE Односторонний поток сервер→клиент. Проще WebSocket для уведомлений
    DNS Рекурсивный резолвер → Root → TLD → Authoritative. Кэшировать с TTL
