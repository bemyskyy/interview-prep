    Generics (Дженерики)¶

    Что такое Дженерики и зачем они нужны?¶

    До Java 5 (2004 год) любая коллекция хранила просто Object. Это порождало три проблемы:

    1. Можно было случайно положить в список строк число — компилятор молчал.
    2. При чтении всегда нужен был ручной каст: String s = (String) list.get(0);
    3. Неправильный каст приводил к ClassCastException в рантайме — уже на продакшене.

    Решение — Generics: Строгая типизация на этапе компиляции (Compile-time Type Safety). Пишешь List<String> — компилятор не пустит туда Integer. Ручные касты не нужны, ошибки выявляются до запуска.

    Стирание типов (Type Erasure): Великая иллюзия¶

    Главный шок: JVM понятия не имеет о существовании дженериков. Для неё нет разницы между List<String> и List<Integer>. В скомпилированном байт-коде никаких угловых скобок нет. Вся магия существует только в исходном коде — для компилятора.

    Что делает компилятор при сборке:

    1. Проверяет, что ты не положил число в список строк.
    2. Стирает все упоминания <String> / <T>. Параметры типа заменяются верхней границей (если ограничений нет — Object).
    3. Там, где ты достаёшь элемент, молча вставляет ручной каст: String s = (String) list.get(0);

    То есть скомпилированный код с дженериками под капотом выглядит в точности как старый код Java 1.4.

    Почему не сделали нормально?

    Интервьюер обязательно спросит: "Почему не научили JVM понимать дженерики, как в C#?"

    Ответ: жажда 100% обратной совместимости. Новый код на Java 5 должен был без проблем работать со старыми библиотеками, скомпилированными на Java 1.4. Гениальный, но костыльный компромисс, за который мы расплачиваемся до сих пор.

    Bridge Methods (Мостовые методы) — вопрос уровня Senior¶

    Из-за стирания типов при наследовании возникает проблема, ломающая полиморфизм.

    В чём проблема:

    public class Node<T> {
    public void setData(T data) { ... }
}

public class MyNode extends Node<Integer> {
    @Override
    public void setData(Integer data) { ... }
}

    После стирания типов компилятор превращает методы в:

    • Родитель: public void setData(Object data)
    • Наследник: public void setData(Integer data)

    Сигнатуры перестали совпадать! Вместо Override получился Overload — полиморфизм сломан.

    Как компилятор спасает ситуацию: Он молча генерирует в MyNode невидимый мостовой метод:

    // Твой метод
public void setData(Integer data) { ... }

// СГЕНЕРИРОВАННЫЙ КОМПИЛЯТОРОМ — ты его не видишь
public void setData(Object data) {
    this.setData((Integer) data); // делегирует твоему методу с кастом
}

    Благодаря этому bridge method сигнатура родителя корректно переопределяется. Полиморфизм спасён.

    Wildcards (?) и принцип PECS¶

    ? extends T (Ковариантность / Upper Bound)¶

    "Этот список хранит объекты класса T или любого его наследника — но я не знаю, какого именно."

    • List<? extends Animal> — сюда можно передать List<Dog>, List<Cat>, List<Animal>.
    • МОЖНО читать: ты уверен, что кто бы там ни лежал — он точно Animal.
    Animal a = list.get(0); // безопасно
    • НЕЛЬЗЯ писать: под маской List<? extends Animal> могут передать List<Cat>. Если добавить new Dog() — собака окажется среди котов. Компилятор запрещает add() для любых элементов (кроме null).

    ? super T (Контравариантность / Lower Bound)¶

    "Этот список хранит объекты класса T или любого его предка (вплоть до Object)."

    • List<? super Dog> — сюда можно передать List<Dog>, List<Animal>, List<Object>.
    • МОЖНО писать: в список Собак, Животных или Объектов можно положить Собаку в любом случае.
    list.add(new Dog()); // безопасно
    • НЕЛЬЗЯ читать как Dog или Animal:** под маской List<? super Dog> могли передать List<Object>, где лежат Стулья, Машины и Коты. Читать можно только как Object obj = list.get(0).

    List<?> vs List<Object> — классическая ловушка¶

    • List<Object> — строго типизирован. Можно и читать, и писать. Но передать List<String> туда нельзя (инвариантность).
    • List<?> — синтаксический сахар для List<? extends Object>. Можно передать List<String> или List<Integer>. Но добавить ничего нельзя (кроме null) — компилятор не знает конкретного типа.

    Железобетонное правило PECS¶

    Джошуа Блох (Effective Java) вывел мнемонику, которую спрашивают на каждом мидл-интервью:

    PECS — Producer Extends, Consumer Super

    Задай себе вопрос: что коллекция делает в этом методе?

    • Producer (поставщик данных) → ? extends T — коллекция только выдаёт данные, ты из неё читаешь.
    • Consumer (потребитель данных) → ? super T — коллекция только принимает данные, ты в неё пишешь.

    Идеальный пример из JDK — метод Collections.copy():

    public static <T> void copy(List<? super T> dest, List<? extends T> src) { ... }
    • src (откуда копируем) — Producer, только читаем → extends.
    • dest (куда копируем) — Consumer, только пишем → super.

    Ограничения типов (Bounds) и Generic-классы¶

    Upper Bound — <T extends SomeClass>¶

    Ограничить тип так, чтобы он был определённым классом или его наследником:

    // Только сущности с полем id — никаких произвольных классов
public class BaseRepository<T extends BaseEntity> {

    public T findById(Long id) { ... }

    public void save(T entity) {
        System.out.println("Saving entity with id: " + entity.getId()); // безопасно!
    }
}

    Без ограничения T extends BaseEntity компилятор не дал бы вызвать entity.getId() — он не знал бы, что у T такой метод есть.

    Множественные ограничения (Multiple Bounds)¶

    Тип можно ограничить сразу несколькими интерфейсами (и одним классом):

    // T обязан быть Animal И реализовывать Serializable И Comparable
public <T extends Animal & Serializable & Comparable<T>> void process(T entity) { ... }

    Ловушка: порядок в Multiple Bounds

    Если среди ограничений есть класс (не интерфейс), он обязан стоять первым. Иначе — ошибка компиляции.

    <T extends Animal & Serializable>   // ✅ класс первый
<T extends Serializable & Animal>   // ❌ ошибка компиляции

    Generic-методы¶

    Параметр типа можно задать не на уровне класса, а на уровне отдельного метода:

    public class Utils {
    // <T> перед возвращаемым типом — это объявление параметра типа метода
    public static <T extends Comparable<T>> T max(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }
}

// Компилятор сам выводит тип:
String s = Utils.max("apple", "banana");   // T = String
Integer i = Utils.max(10, 42);             // T = Integer

    Главные запреты Generics (Ловушки компилятора)¶

    Интервьюеры обожают давать куски кода и спрашивать: "Скомпилируется ли это? Если нет — почему?"

    Нельзя создать экземпляр new T()¶

    public class Box<T> {
    public T create() {
        return new T(); // ❌ ОШИБКА КОМПИЛЯЦИИ
    }
}

    Почему: После стирания типов T превращается в Object. Компилятор не знает, какой конструктор вызывать. Что, если у конкретного T нет конструктора без аргументов?

    Решение через Supplier или рефлексию:

    public <T> T create(Supplier<T> supplier) {
    return supplier.get(); // ✅
}
// Использование:
Box<String> box = create(String::new);

    Нельзя создать массив Generic-типа¶

    T[] arr = new T[10];              // ❌ ошибка компиляции
List<String>[] arr = new List[10]; // ❌ ошибка компиляции (unchecked warning)

    Почему: Массивы в Java проверяют тип элементов в рантайме (они ковариантны). Но в рантайме T уже стёрт до Object. JVM не смогла бы проверить, что ты кладёшь в массив нужный тип — это открывало бы дыру в безопасности типов.

    Решение:

    @SuppressWarnings("unchecked")
T[] arr = (T[]) new Object[10];  // обходной путь через каст

// Или через рефлексию (более безопасно):
T[] arr = (T[]) Array.newInstance(clazz, 10);

    Нельзя использовать примитивы¶

    List<int> list = new ArrayList<>();    // ❌ ошибка компиляции
List<double> list = new ArrayList<>(); // ❌ ошибка компиляции

    Почему: После стирания типов параметр превращается в Object. Примитивы (int, double) не наследуются от Object — они вообще не объекты. JVM не может положить int туда, где ожидается ссылка на объект.

    Решение — классы-обёртки:

    List<Integer> list = new ArrayList<>();  // ✅ autoboxing/unboxing делает остальное

    Именно поэтому существуют Integer, Double, Long и другие обёртки — они позволяют примитивам жить в дженерик-коллекциях.

    Нельзя делать статические поля типа T¶

    public class Box<T> {
    private static T instance; // ❌ ошибка компиляции
}

    Почему: Статическое поле одно на весь класс, а не на каждый экземпляр. Box<String> и Box<Integer> — это один и тот же класс в байт-коде. Какой тип должен иметь instance — String или Integer? Противоречие нерешаемо.

    Heap Pollution и Raw Types¶

    Raw Types (Сырые типы) — красный флаг на ревью¶

    Raw type — это использование дженерик-класса без угловых скобок в современном коде:

    List list = new ArrayList();  // ❌ Raw type — компилятор выдаёт предупреждение
list.add("Текст");
list.add(42);

String s = (String) list.get(1); // ClassCastException в рантайме!

    Компилятор видит List без типа и "отключает" проверку типов для него. Любые ошибки снова переезжают в рантайм.

    Raw Types в современном коде

    Raw types существуют только для совместимости с кодом до Java 5. В любом новом коде их использование — это красный флаг на код-ревью. Если видишь Raw type без @SuppressWarnings("rawtypes") и объяснения — это баг.

    Heap Pollution (Загрязнение кучи)¶

    Heap Pollution — это ситуация, когда переменная дженерик-типа ссылается на объект, не совместимый с её параметром типа. Возникает при смешивании Raw types и дженериков:

    List<String> strings = new ArrayList<>();
List rawList = strings;          // Raw type — компилятор предупреждает, но пускает
rawList.add(42);                 // добавляем Integer в List<String>!

String s = strings.get(0);      // ClassCastException в рантайме — куча "загрязнена"

    Особенно коварна ситуация с Varargs и дженериками.

    @SafeVarargs — Когда и зачем¶

    Varargs под капотом — это массив. А массивы дженериков создавать нельзя (мы разбирали выше). Поэтому компилятор всегда ругается на такую комбинацию:

    public static <T> void addAll(List<T> list, T... elements) { // ⚠️ unchecked warning
    for (T e : elements) list.add(e);
}

    Компилятор создаёт Object[] для elements — и кто угодно мог бы передать туда значение не того типа.

    Аннотация @SafeVarargs — это твоё торжественное обещание компилятору: "Я гарантирую, что внутри метода varargs-массив используется только для чтения и не передаётся наружу. Heap Pollution невозможен."

    @SafeVarargs // ✅ глушим предупреждение — метод действительно безопасен
public static <T> List<T> listOf(T... elements) {
    return Arrays.asList(elements); // только читаем — безопасно
}

    Когда НЕ ставить @SafeVarargs

    Если внутри метода varargs-массив передаётся в другой метод или сохраняется в поле — ставить аннотацию нельзя. Это будет ложь компилятору, которая обернётся ClassCastException в рантайме.

    @SafeVarargs // ❌ ОПАСНО — передаём массив наружу!
public static <T> T[] toArray(T... elements) {
    return elements; // Heap Pollution гарантирован
}
