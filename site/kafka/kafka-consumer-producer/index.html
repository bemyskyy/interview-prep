    Kafka: Механика Consumer и Producer¶

    Ключи и гарантия порядка¶

    1. Почему нет глобального порядка (цена скорости)¶

    Пользователи генерируют 10 000 событий/сек. Если бы Kafka гарантировала глобальный порядок — пришлось бы складывать всё в один лог (одну партицию) и читать одним потоком. Система захлебнулась бы.

    Компромисс Kafka: распиливаем топик на партиции (например, 3), читаем параллельно, но жертвуем глобальным порядком.

    Но бизнесу часто плевать на глобальный порядок! Неважно что привычка Пети обработана раньше привычки Васи. Критично только одно: события одной конкретной привычки должны обрабатываться строго по очереди — сначала "создана", потом "выполнена", а не наоборот.

    Решение — Ключи (Keys).

    2. Отправка без ключа (хаос и балансировка)¶

    Сообщение состоит из Key и Value. Ключ не обязателен. Что будет с пустым ключом (Key = null)?

    Kafka включит Round-Robin: первое сообщение → Партиция 0, второе → Партиция 1, третье → Партиция 2, четвёртое → снова 0.

    ❌ Как ломается порядок:
1. Событие 1 (Привычка 42 создана)  → Партиция 0
2. Событие 2 (Привычка 42 удалена)  → Партиция 1

Консьюмер Партиции 1 оказался быстрее:
   вычитал "Событие 2" → лезет в БД удалять привычку 42 →
   а её ещё нет! → EntityNotFoundException
Через миллисекунду второй консьюмер создаёт привычку.
Бизнес-логика сломана.

    3. Магия ключей (хэширование)¶

    Указываем явный ключ. Для привычек идеальный ключ — её habitId = "42".

    Формула: Hash(Key) % Number_of_Partitions

1. Продюсер берёт ключ "42"
2. Прогоняет через хэш-функцию (по умолчанию Murmur2) → 8462947
3. Остаток от деления на количество партиций: 8462947 % 3 = 1
4. Сообщение летит строго в Партицию 1

    Почему это гарантирует порядок: хэш от "42" всегда = 8462947. Математика не меняется. Все события этой привычки (создание, апдейт, выполнение, удаление) 100% попадут в одну Партицию 1. А партицию читает всегда один консьюмер строго последовательно → события обработаются ровно в том порядке, в котором сгенерированы.

    Убийственный вопрос на собесе

    "Порядок работает. Через полгода трафик вырос в 10 раз. Добавляете ещё 2 партиции (итого 5). Что произойдёт с порядком?"

    Ответ: Порядок сломается для существующих сущностей. Меняется знаменатель в формуле Hash(Key) % 5. Тот же ключ "42", который всю жизнь летел в Партицию 1, теперь может дать остаток 4 и полететь в Партицию 4. Старые события в первой партиции, новые в четвёртой — их читают разные консьюмеры параллельно, Race Condition вернулся.

    Архитектурное правило

    Количество партиций в топиках, где важен порядок по ключу, нельзя менять на лету. Закладывай количество с запасом (Over-provisioning) на этапе проектирования — например, сразу 50 партиций, даже если сейчас всего 2 инстанса приложения.

    Consumer Groups (Группы потребителей)¶

    1. Что такое Consumer Group¶

    Поднимая инстанс Spring Boot приложения, читающего Kafka, ты обязан указать group.id (например, appointment-processor).

    Consumer Group — логическое объединение инстансов одного приложения, работающих над общей задачей. Для брокера вся группа выглядит как один «виртуальный супер-потребитель».

    2. Золотое правило Kafka¶

    Главное правило балансировки

    Одна партиция в рамках одной Consumer Group может читаться только ОДНИМ консьюмером.

    Почему так жёстко? Из-за гарантии порядка. Если Kafka отдаст Партицию 0 двум инстансам, они начнут вытаскивать сообщения параллельно (Race Condition) — порядок для одного ключа мгновенно сломается.

    3. Классическая задача: 3 партиции и 5 консьюмеров¶

    Топик payments с 3 партициями, запущено 5 инстансов (один group.id):

Консьюмер 1 → Партиция 0
Консьюмер 2 → Партиция 1
Консьюмер 3 → Партиция 2
Консьюмер 4 → Idle (простаивает)
Консьюмер 5 → Idle (простаивает)

    Вопрос-ловушка

    "Зачем запустили 2 лишних инстанса, если они простаивают и жгут ресурсы?"

    Ответ: Ради отказоустойчивости (High Availability). Это горячий резерв. Если работающий сервер упадёт (OOM, потеря сети) — сработает Rebalance, и простаивающий консьюмер за миллисекунды подхватит осиротевшую партицию. Простой минимален.

    4. Несколько Consumer Groups (паттерн Pub/Sub)¶

    То, ради чего выбирают Kafka вместо классических брокеров. Один топик appointments-events, разные группы читают независимо:

                        ┌─→ crm-core-group      → PostgreSQL (календарь)
appointments-events ├─→ notification-group  → SMS клиенту
                    └─→ analytics-group      → дашборды владельца
    • crm-core-group — основной бэкенд, кладёт запись в PostgreSQL.
    • notification-group — читает те же события, шлёт SMS.
    • analytics-group — тяжёлая аналитика, вычитывает раз в час.

    Физически: каждая группа имеет свой независимый оффсет. Нотификации обрабатывают за 10мс и убегают вперёд, аналитика тормозит на 5 минут. Читают одни и те же физические файлы партиций. Никто никого не блокирует, сообщения не удаляются после первого прочтения. Идеальная развязка (decoupling) микросервисов.

    Rebalancing (Ребалансировка)¶

    1. Что это¶

    Перераспределение партиций между живыми консьюмерами внутри группы. Цель — гарантировать что каждая партиция читается ровно одним консьюмером и ни одна не осталась «брошенной».

    2. Три триггера¶

    1. Падение инстанса      — консьюмер упал (OOM, питание, сеть)
2. Масштабирование       — добавили новый инстанс, Kafka даёт ему партиции
3. Изменение топологии   — админ добавил новые партиции в топик

    3. Два вида пульса — как Kafka понимает что сервер «умер»¶

    Сетевой пульс (session.timeout.ms):
  Фоновый поток шлёт heartbeat брокеру.
  Нет пульса дольше session.timeout.ms (~10 сек) → сервер физически умер → ребаланс

Пульс бизнес-логики (max.poll.interval.ms):
  Сеть есть, но код завис на тяжёлом SQL или дедлоке.
  Между вызовами poll() прошло > max.poll.interval.ms (дефолт 5 мин) →
  сервис "зомби" (жив в сети, работу не делает) → выкидываем из группы

    4. Как физически происходит ребаланс¶

    Брокер НЕ решает кому какая партиция

    Многие думают что брокер сам распределяет партиции. Ошибка! Kafka делегирует эту логику клиентам.

    Group Coordinator (брокер) — следит кто жив, подаёт сигнал к сбору
Group Leader (твоё приложение) — один из живых консьюмеров, применяет алгоритм

Фаза JoinGroup:
  Все живые консьюмеры шлют "я жив" Координатору
  Координатор собирает список, отдаёт Лидеру

Фаза SyncGroup:
  Лидер (твой Spring Boot сервис) сам применяет алгоритм распределения
  (Round Robin) → отправляет план Координатору → Координатор рассылает всем

    Почему так? Чтобы брокер оставался «глупым» и быстрым. Логика распределения в клиентской библиотеке — можно написать свой Partition Assignor, не трогая код сервера Kafka.

    5. Cooperative Rebalancing — киллер-фича¶

    Eager Rebalancing (до Kafka 2.4) — при ребалансе ВСЕ консьюмеры бросали работу, отпускали ВСЕ партиции, ждали нового распределения. Полная остановка (Stop-The-World). На большой группе пауза — секунды и даже минуты.

    Козырь сеньора

    С Kafka 2.4+ (и в современном Spring Kafka) по умолчанию Incremental Cooperative Rebalancing. Добавляешь новый сервер → старые серверы не бросают всю работу. Лидер просит отдать только те конкретные партиции, что нужны новичку. Остальные читаются без остановок. Никакого глобального простоя.

    Итоговая шпаргалка¶

    Тема Запомнить
    Ключ сообщения Hash(Key) % партиции. Один ключ → всегда одна партиция → порядок
    Без ключа Round-Robin по партициям. Порядок не гарантирован
    Смена числа партиций Ломает порядок для существующих ключей. Закладывай с запасом
    Consumer Group Инстансы одного приложения. Для брокера — один супер-потребитель
    Правило партиции Одна партиция = один консьюмер в группе. Лишние — горячий резерв
    Несколько групп Pub/Sub: каждая группа свой оффсет, читают одни файлы независимо
    Триггеры ребаланса Падение / масштабирование / изменение топологии
    Два пульса session.timeout.ms (сеть) + max.poll.interval.ms (бизнес-логика)
    Кто распределяет Group Leader (клиент), не брокер. Брокер — только Coordinator
    Cooperative Rebalance Kafka 2.4+. Не Stop-The-World, отдаются только нужные партиции
