# Kafka: Физика брокера

## Topic и Partition

### 1. Распределённый лог против классической очереди

Частый вопрос на собесах — сравнить Kafka с RabbitMQ/ActiveMQ. Главное отличие в архитектурном подходе.

**Классическая очередь (RabbitMQ): «Умный брокер — глупый потребитель»**

- Брокер получает сообщение и пушит (Push) его консьюмеру. После подтверждения (ACK) брокер **навсегда удаляет** сообщение.
- Минусы: брокер тратит ресурсы на отслеживание кому отдал сообщение и получил ли ответ. Удалённое сообщение прочитать заново невозможно (если упала БД и данные не сохранились).

**Kafka (распределённый лог): «Глупый брокер — умный потребитель»**

- Kafka не удаляет сообщения после прочтения. Работает как **Append-Only Log** — сообщения пишутся на диск друг за другом, иммутабельны (нельзя изменить или удалить поштучно).
- Брокер ничего не пушит. Консьюмеры сами вытягивают (Pull) данные когда удобно. Сообщения хранятся столько, сколько указано в `retention.ms` (например, 7 дней).
- Плюс: если сервис упал или в логике была ошибка — можно «отмотать» время назад и перечитать те же сообщения.

| | **RabbitMQ (очередь)** | **Kafka (лог)** |
|---|---|---|
| **Модель доставки** | Push (брокер → консьюмер) | Pull (консьюмер ← брокер) |
| **После прочтения** | Сообщение удаляется | Хранится до retention |
| **Перечитать** | Невозможно | Отмотать оффсет назад |
| **Где логика** | В брокере | В консьюмере |

### 2. Topics — логическая абстракция

**Топик** — имя категории/папки для сообщений одного типа (`user-registrations`, `payment-events`).

Топик не существует физически как единый файл. Для ОС сервера Kafka «топик» — это просто набор директорий. Физическая реальность начинается на уровне партиций.

### 3. Partitions — физическая реальность

Каждый топик разбивается на **партиции**. Создавая топик `orders`, ты обязан указать на сколько партиций его распилить (например, 3).

- **Физически** — партиция это буквально файл (сегмент лога) на диске брокера. Новые сообщения дописываются строго в конец.
- **Offset (Смещение)** — каждое сообщение внутри партиции получает уникальный возрастающий порядковый номер. Первое — offset 0, второе — 1, миллионное — 999999.

!!! warning "Гарантия порядка"
    Строгий порядок сообщений гарантируется **только внутри одной партиции**. Kafka НЕ гарантирует, что сообщение из Партиции 0 было отправлено раньше, чем из Партиции 1.

### 4. Почему партиция — единица масштабирования

Ключевой вопрос на понимание горизонтального масштабирования.

```
Топик payments с 1 партицией:
  Сколько бы консьюмеров ни запустил (2, 5, 100) —
  читать эту партицию сможет ТОЛЬКО ОДИН.
  Остальные простаивают. (Защита от Race Condition.)

Топик payments с 10 партициями:
  1. Масштабирование брокеров — 10 файлов раскидываются по 10 серверам.
     Нагрузка на запись распределена между 10 дисками.
  2. Масштабирование консьюмеров — 10 инстансов приложения,
     Kafka отдаёт каждому по партиции. Читают параллельно.
     Производительность ×10.
```

!!! tip "Правило масштабирования"
    Партиция — минимальная гранула параллелизма в Kafka. Упёрся в лимиты обработки → первым делом увеличивай количество партиций и добавляй консьюмеры.

## Offset

### 1. Оффсет партиции (взгляд брокера / физика)

Партиция — бесконечный лог-файл. Продюсер прислал сообщение → брокер дописал в конец → присвоил уникальный возрастающий номер. Это **оффсет партиции**.

- **Неизменен** — сообщение с оффсетом `42` навсегда останется под номером `42` (пока не истечёт `retention.ms`).
- **Log End Offset (LEO)** — указатель на конец файла. Если в партиции 100 сообщений (0–99), LEO = 100. Сюда запишется следующее входящее.

### 2. Оффсет консьюмера (взгляд потребителя / логика)

Оффсет консьюмера — **виртуальная «закладка» в книге**. Сервис читает данные и отмечает прогресс, чтобы при перезапуске не читать всё сначала.

```
1. Консьюмер скачал пачку сообщений: оффсеты 10, 11, 12
2. Обработал бизнес-логикой, сохранил в БД
3. Отправил Kafka команду: "Всё обработал, мой прогресс — оффсет 13"
   ↑ это называется Commit (коммит)
```

### 3. Где Kafka хранит эти закладки? (вопрос для Senior)

_"Консьюмер закоммитил оффсет. Куда физически Kafka его записала? Не в память же?"_

- **Раньше (каменный век):** Kafka хранила оффсеты в Zookeeper. Но Zookeeper не был рассчитан на миллионы операций записи в секунду — стал узким горлышком.
- **Сейчас:** Kafka хранит оффсеты **внутри самой себя** — в скрытом системном топике `__consumer_offsets`.

```
При коммите консьюмер работает как продюсер —
отправляет служебное сообщение в __consumer_offsets:

  Ключ:     [Consumer Group + Топик + Номер Партиции]
  Значение: число (например, 13)

При перезагрузке сервис идёт в __consumer_offsets,
находит свою последнюю цифру по ключу и говорит брокеру:
"Давай данные из партиции, начиная с 13-го сообщения"
```

## Retention Policy

### 1. Почему удалять по одному сообщению — самоубийство

Партиция — Append-Only Log. В файле миллион сообщений, консьюмер прочитал сообщение №5. Что если Kafka попытается его удалить?

Придётся либо оставить "дырку" (фрагментация), либо сдвинуть 999 995 сообщений вверх. И то, и другое убьёт скорость диска.

!!! info "Почему Kafka такая быстрая"
    Kafka пишет и читает со скоростью RAM благодаря Page Cache в Linux и последовательному I/O. Запись в конец файла — **O(1)**. Поштучное удаление превратило бы это в O(N) и уничтожило пропускную способность.

### 2. Как Kafka на самом деле удаляет данные (сегменты)

Kafka работает не с отдельными сообщениями, а с файлами-сегментами.

```
Партиция физически = не один гигантский файл, а куски (Segments)
                     размер сегмента по умолчанию = 1 ГБ

┌──────────┬──────────┬──────────┬─────────────┐
│ Segment1 │ Segment2 │ Segment3 │ Active Seg  │ ← сюда пишет продюсер
│ (закрыт) │ (закрыт) │ (закрыт) │ (не удалить)│
└──────────┴──────────┴──────────┴─────────────┘
     ↑
Log Cleaner проверяет: возраст самого свежего сообщения
в сегменте > retention.ms (7 дней)?
Да → удаляет ВЕСЬ 1 ГБ файл целиком на уровне ОС. Мгновенно.
```

Активный сегмент (последний, куда пишет продюсер) Kafka не удалит никогда, даже если вышло время.

### 3. Настройки Retention: время или объём

Политика очистки настраивается для каждого топика. Два триггера:

```
1. По времени (log.retention.hours / ms):
   удалять сегменты старше N дней (дефолт 7 дней)

2. По размеру (log.retention.bytes):
   удалять старые сегменты если размер партиции > N ГБ
   (лимит 50 ГБ → выросла до 51 ГБ → удаляется старейший сегмент)
```

Работают по принципу «ИЛИ» — что наступит раньше, то и удалит старые данные.

### 4. Зачем хранить данные неделями (бизнес-смысл)

- **Машина времени (Replayability)** — упала БД или выкатил кривой код? Сообщения не потеряны. Чинишь баг, отматываешь оффсет назад, перечитываешь логи за 3 дня. С RabbitMQ невозможно — данные сгорели бы после первого прочтения.
- **Независимость множества систем** — данные лежат 7 дней. Сервис уведомлений читает за миллисекунду, тяжёлый сервис аналитики выкачивает раз в сутки батчами. Данные дождутся всех.
- **Event Sourcing** — топик с `retention.ms = -1` (бесконечное хранение) становится Source of Truth всей системы за всю историю.

### 5. Log Compaction — киллер-фича для интервью

_"Не хочу удалять по времени, но и бесконечно растить диск не могу. Топик с балансами юзеров — важен только текущий последний баланс."_

Козырь: **Log Compaction** (`cleanup.policy=compact`). Вместо удаления по времени, Kafka в фоне пробегается по старым сегментам, смотрит на **ключи** и удаляет все старые версии, оставляя **только последнее сообщение для каждого уникального ключа**.

```
По ключу user-123 было 50 изменений профиля за год:
  user-123 → {баланс: 100}   ┐
  user-123 → {баланс: 250}   ├─ удаляются
  user-123 → {баланс: 180}   ┘
  user-123 → {баланс: 4000}  ← остаётся только последнее

Позволяет хранить справочники и стейты вечно, не раздувая диск.
```

## Итоговая шпаргалка

| **Тема** | **Запомнить** |
|---|---|
| **Kafka vs RabbitMQ** | Kafka — Pull-лог, хранит после чтения. RabbitMQ — Push-очередь, удаляет |
| **Topic** | Логическая абстракция, набор директорий. Физика — на уровне партиций |
| **Partition** | Файл на диске, Append-Only. Порядок гарантирован только внутри партиции |
| **Партиция = масштаб** | Одна партиция = один консьюмер. Больше партиций = больше параллелизма |
| **Offset партиции** | Неизменный номер сообщения. LEO = конец файла |
| **Offset консьюмера** | «Закладка» прогресса. Commit сохраняет позицию |
| **`__consumer_offsets`** | Скрытый топик где Kafka хранит оффсеты (раньше был Zookeeper) |
| **Retention** | Удаление целыми сегментами (1 ГБ), не по одному. По времени ИЛИ размеру |
| **Сегменты** | Партиция нарезана на куски. Активный сегмент не удаляется |
| **Log Compaction** | `cleanup.policy=compact` — оставить последнее сообщение на каждый ключ |
