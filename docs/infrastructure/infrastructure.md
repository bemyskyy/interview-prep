# Инфраструктура (DevOps)

## Контейнеризация (Docker)

### Какую проблему решает Docker

На твоём ноутбуке Java 17, своя версия PostgreSQL, настройки таймзон — всё работает. Передаёшь `.jar` на прод, а там Java 11 и нет переменных окружения — всё падает.

**Docker убивает "на моей машине работало".** Упаковывает приложение вместе со всей средой (куском ОС, JDK, библиотеками, конфигами) в стандартизированный "ящик", который работает идентично везде.

### Контейнер vs Виртуальная машина

| | **Виртуальная машина** | **Docker-контейнер** |
|---|---|---|
| **ОС** | Полноценная гостевая ОС со своим ядром | Нет своей ОС — переиспользует ядро хоста |
| **Вес** | Гигабайты | Мегабайты |
| **Старт** | Минуты | Миллисекунды |
| **Изоляция** | Полная (гипервизор) | Процесс с иллюзией изоляции |
| **Накладные расходы** | Высокие (вторая ОС вхолостую) | Минимальные |

Контейнер — это обычный процесс Linux, вокруг которого ОС выстроила "стены иллюзии", заставляя думать что он на сервере один.

### Святая троица Docker

```
Dockerfile (чертёж)  →  Image (образ)  →  Container (контейнер)
текстовые инструкции    иммутабельный        запущенный экземпляр
                        Read-Only слепок     в оперативной памяти

Аналогия с Java:        Image = class        Container = new Object()
```

### Магия ядра Linux (сеньорский козырь)

Вся изоляция держится на двух технологиях ядра:

- **Namespaces (изоляция)** — ограничивают что контейнер **видит**. Процесс думает что у него свой корень файловой системы `/`, своя сетевая карта, что он главный процесс (PID 1).
- **Cgroups (лимиты)** — ограничивают что контейнер **использует**. Не дадут Java-приложению с утечкой памяти сожрать все 64 ГБ и положить соседей. "Убей процесс если превысит 1 ГБ".

### Анатомия идеального Dockerfile

**1. Multi-stage сборка**

```dockerfile
# STAGE 1: Builder (тяжёлый образ для сборки)
FROM maven:3.8.5-openjdk-17-slim AS builder
WORKDIR /build

# Кэшируем зависимости ОТДЕЛЬНЫМ слоем (меняются редко)
COPY pom.xml .
RUN mvn dependency:go-offline

# Только теперь копируем код (меняется часто)
COPY src ./src
RUN mvn clean package -DskipTests

# STAGE 2: Runner (лёгкий и безопасный)
FROM gcr.io/distroless/java17-debian11
WORKDIR /app
COPY --from=builder /build/target/app.jar ./app.jar
ENV JAVA_OPTS="-XX:+UseG1GC -XX:MaxRAMPercentage=75.0"
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Без multi-stage итоговый образ 1ГБ+ (исходники, кэш Maven, утилиты сборки). С multi-stage — 150 МБ (только JRE + jar). Исходного кода в проде физически нет.

!!! warning "Ловушка с порядком COPY"
    ```dockerfile
    # ❌ Плохо — любое изменение кода инвалидирует кэш зависимостей
    COPY . .
    RUN mvn clean package   # каждый раз качает пол-интернета заново

    # ✅ Хорошо — зависимости в отдельном слое
    COPY pom.xml .
    RUN mvn dependency:go-offline   # кэшируется намертво до изменения pom.xml
    COPY src ./src
    RUN mvn clean package -DskipTests
    ```
    Каждая `RUN`/`COPY` создаёт слой. Docker кэширует неизменённые слои. Зависимости меняются редко, код — постоянно, поэтому их разделяют.

**2. Битва базовых образов**

| Образ | Вес | Особенность |
|---|---|---|
| `openjdk:17` (Debian) | ~300 МБ | Куча утилит, большая поверхность атаки |
| `eclipse-temurin:17-jre-alpine` | ~5 МБ ОС | Лёгкий, но `musl libc` вместо `glibc` — иногда странности с JNI/шрифтами |
| `gcr.io/distroless/java17` | минимум | Нет ничего, даже `/bin/sh` и пакетного менеджера |

!!! tip "Distroless — козырь по безопасности"
    Если приложение взломали (Log4Shell) и хакер хочет открыть консоль или скачать вирус через `wget` — в Distroless нет ни `bash`, ни `wget`. Взломщик в запертой пустой комнате.

**3. Non-Root User**

```dockerfile
# По умолчанию контейнер работает под root.
# Прорыв изоляции → хакер root на хост-сервере. Катастрофа.
RUN addgroup -S spring && adduser -S spring -G spring
USER spring:spring
```

### Docker Compose

**1. Внутренний DNS (прощай localhost)**

```yaml
services:
  postgres-db:        # ← это имя становится хостнеймом
    image: postgres:15
  crm-backend:
    image: backend:latest
    # В application.yml: jdbc:postgresql://postgres-db:5432/booking
    # Никаких localhost и хардкода IP!
```

Docker Compose создаёт виртуальную сеть, поднимает встроенный DNS. Имя сервиса = хостнейм.

!!! note "Ports vs Expose"
    `ports: ["5432:5432"]` пробрасывает порт наружу (для DBeaver с твоего ноута). Если сервис нужен только внутри (Redis для бэкенда) — блок `ports` не пишут вообще, контейнеры и так видят друг друга. Базовая безопасность.

**2. Проблема гонки: healthcheck + depends_on**

```yaml
services:
  postgres-db:
    image: postgres:15
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5

  crm-backend:
    depends_on:
      postgres-db:
        condition: service_healthy   # ждёт пока healthcheck скажет OK
```

Spring Boot стартует за 3 сек, БД ещё инициализируется → `ConnectionRefusedException`. Решение джуна — `wait-for-it.sh` или `Thread.sleep()`. Решение сеньора — `healthcheck` + `depends_on`.

**3. Volumes — сохранение данных**

```yaml
services:
  postgres-db:
    volumes:
      - pg_data:/var/lib/postgresql/data
volumes:
  pg_data:   # данные переживут docker-compose down
```

**4. Kafka KRaft (без Zookeeper)**

!!! tip "Козырь 2026 года"
    Если рассказываешь как поднимаешь Zookeeper для Kafka — интервьюер скривится. С Kafka 3.3 Zookeeper deprecated. KRaft (Kafka Raft) — Kafka сама хранит метаданные через консенсус Raft. Минус контейнер, меньше RAM, старт в 2 раза быстрее.

**5. Profiles — изоляция процессов**

```yaml
services:
  analytics:
    profiles: ["analytics"]   # не запустится при обычном up
# docker-compose up                      → только базовые сервисы
# docker-compose --profile analytics up  → всё включая тяжёлое
```

### Сети Docker

| Драйвер | Как работает | Когда |
|---|---|---|
| **bridge (default)** | Контейнеры по IP, без DNS | Редко используется напрямую |
| **bridge (user-defined)** | Контейнеры по именам, есть DNS | Docker Compose создаёт автоматически |
| **host** | Делит сетевой стек с хостом, без NAT | Максимальная скорость, ноль изоляции |

!!! tip "Сегментация сетей — паттерн безопасности"
    Сеньор не суёт все контейнеры в одну сеть. Создаёт `frontend-net` и `backend-net`. Nginx подключён к обеим. Микросервисы и БД — только к `backend-net`. Взломали фронтенд-контейнер → хакер физически не может отправить пакет в БД, между ними нет сетевого маршрута на уровне ядра.

### Volumes — постоянство данных

Образ — слои Read-Only. При запуске поверх создаётся тонкий **Writable Layer** (Copy-on-Write). При `docker rm` этот слой уничтожается вместе со всеми данными.

| | **Bind Mount** | **Named Volume** |
|---|---|---|
| **Синтаксис** | `-v /Users/me/logs:/app/logs` | `-v pg_data:/var/lib/postgresql/data` |
| **Управление** | Ты указываешь папку на хосте | Docker сам управляет в `/var/lib/docker/volumes` |
| **Когда** | Локальная разработка (Hot Reload) | Продакшн: БД, Kafka, Redis |

!!! warning "Вопрос на засыпку про данные"
    _"PostgreSQL в Docker с Named Volume. Что с данными при `docker stop/start`? При `docker rm` + новый контейнер с тем же томом? При выключении питания?"_

    1. `stop/start` — контейнер не уничтожается, данные на месте.
    2. `rm` — контейнер уничтожен, но **Named Volume живёт независимо**. Новый контейнер с тем же томом подхватит данные.
    3. Выключение питания — данные в Volume на диске. Но есть риск потерять последние транзакции из кэша записи ОС, не успевшие в `fsync`. Защита — строгая синхронизация в самой СУБД (`wal_level` в Postgres).

## CI/CD

### Философия

- **CI (Continuous Integration)** — каждый коммит автоматически собирается и тестируется. Цель — рано обнаружить что код сломал что-то.
- **CD (Continuous Delivery)** — артефакт собирается автоматически, на прод катится по кнопке человеком.
- **CD (Continuous Deployment)** — всё на 100% автоматизировано, тесты прошли → код летит на прод сам.

### Анатомия Java-пайплайна

```
Build → Test → Build Image → Deploy
  │       │         │           │
компиляция тесты   Docker     обновление
mvn      unit +    multi-stage образа в
compile  integration → Registry  кластере
```

**Build** — Runner скачивает код, `mvn clean compile`. Сеньор кэширует `~/.m2` — если `pom.xml` не менялся, зависимости из кэша за секунду.

**Test** — `mvn test` (unit) + `mvn verify` (интеграционные с Testcontainers).

!!! tip "Ловушка: медленные тесты"
    _"Интеграционные тесты идут 20 минут, разработчики жалуются."_ Разделять по стадиям: быстрые unit на каждый коммит, тяжёлые интеграционные параллельно (Parallel Jobs) или только при Merge Request в master.

**Build Image** — собирается Docker-образ, тегируется (`v1.2.42` или хэш коммита), отправляется в Registry (Nexus, Harbor, GitLab Registry).

**Deploy** — Runner подключается к кластеру (K8s API/SSH), обновляет образ.

!!! warning "Secrets никогда в коде"
    Пароли, ключи, токены запрещено хранить в `.gitlab-ci.yml`. Только через Masked Variables в настройках CI/CD или HashiCorp Vault.

### Стратегии деплоя

```
Rolling Update:  старые контейнеры гасятся по очереди, новые поднимаются
                 [v1][v1][v1] → [v2][v1][v1] → [v2][v2][v1] → [v2][v2][v2]
                 Стандарт K8s. Падает новый → деплой останавливается

Blue-Green:      рядом со старой (Blue) поднимается новая (Green)
                 балансировщик переключает 100% трафика за миллисекунду
                 Что-то не так → мгновенный откат на Blue

Canary:          новая версия на 5% юзеров → смотрим Grafana →
                 ошибок нет → плавно повышаем до 100%
```

## Миграции БД (Flyway / Liquibase)

### Проблема ручных обновлений

Добавил сущность `Review` → нужна таблица `reviews`. Кидаешь `CREATE TABLE` админу в Telegram "накати перед деплоем". Админ забыл / накатил не в ту базу / ошибся → новый код падает с `PSQLException`. Человеческий фактор.

### Решение: версионирование БД

```
src/main/resources/db/migration/
  ├── V1__init.sql
  ├── V2__add_reviews.sql
  └── V3__add_indexes.sql
```

Flyway создаёт служебную таблицу `flyway_schema_history`, записывает применённые скрипты. При старте сверяет файлы с таблицей и накатывает **только новые**.

### Интеграция с CI/CD

- **Встроенный в Spring Boot** — добавляешь зависимость, Flyway запускается ДО Tomcat, накатывает миграции, потом приложение оживает.
- **Отдельный шаг пайплайна** — для огромных баз (индекс на таблице 500ГБ идёт часами). Spring Boot ждал бы долго, K8s решил бы что контейнер завис (Liveness Probe) и убил. Поэтому: `Build → Test → Build Image → DB Migrate → Deploy`.

### Козыри для интервью

!!! tip "Валидация чексумм"
    _"Что если разработчик изменит уже применённый `V1__init.sql`?"_

    Приложение не запустится (`FlywayException`). Flyway хранит хэш каждого скрипта. При старте пересчитывает — если хоть пробел изменился, красная тревога. Исправлять — только новым скриптом `V4__fix.sql`. Старые иммутабельны (как сообщения в Kafka).

!!! tip "Распределённая блокировка"
    _"5 инстансов стартуют одновременно при деплое и все бросятся делать CREATE TABLE. Гонка?"_

    Нет. Первый добежавший делает `SELECT FOR UPDATE` на `flyway_schema_history` (эксклюзивный лок). Остальные 4 ждут. Первый накатил, отпустил лок → остальные видят что версия обновлена и продолжают загрузку.

!!! warning "Zero-Downtime: обратная совместимость"
    При Blue-Green старая и новая версии работают одновременно. **Миграции не должны ломать старый код.**

    ❌ Нельзя сразу переименовать `client_name` → `name` (старая версия посыпется).

    ✅ В 3 релиза: (1) создать `name`, писать в обе колонки; (2) фоновый скрипт копирует данные, читаем из `name`; (3) удалить `client_name`.

## Оркестрация (Kubernetes)

Когда проект вырастает из одного сервера, Docker Compose не справляется. Кластером управляет K8s.

- **Pods & Deployments** — K8s плавно обновляет версии (Rolling Update): поднимает новый контейнер, ждёт готовности, гасит старый, не обрывая запросы.
- **Services & Ingress** — как внешний трафик маршрутизируется внутрь кластера и балансируется между инстансами.
- **ConfigMaps & Secrets** — прокидывание логинов, паролей, переменных окружения извне, без хардкода в `application.yml`.

## Observability (Наблюдаемость)

Когда прод падает, нет возможности зайти по SSH и читать логи глазами. Нужны инструменты расследования.

**Централизованное логирование (ELK / EFK)** — Elasticsearch + Logstash/Fluentd + Kibana. Логи со всех контейнеров в одном месте. Сеньор пишет структурированные JSON-логи и прокидывает `traceId` (MDC в логгере), чтобы найти всю цепочку вызовов одного запроса через 5 микросервисов.

**Метрики (Prometheus + Grafana)** — сбор метрик через Spring Boot Actuator + Micrometer. Сколько памяти в Heap, сколько активных соединений в HikariCP, какой процент ответов API возвращает 500.

**Три столпа Observability:**

```
Logs    — что произошло (текстовые записи событий)
Metrics — сколько/как часто (числовые показатели во времени)
Traces  — где именно (путь запроса через микросервисы, traceId)
```

## Web-серверы и API Gateway

**Reverse Proxy (Nginx / HAProxy)** — балансировка нагрузки, терминация SSL (HTTPS снаружи → HTTP внутри защищённого контура), кэширование статики.

**API Gateway (Spring Cloud Gateway)** — единая точка входа. Проверка JWT-токенов, защита от DDoS (Rate Limiting), маршрутизация к нужному микросервису.
