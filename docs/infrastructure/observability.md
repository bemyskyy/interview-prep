# Observability

Как понять, что происходит в проде, не заходя на серверы: метрики, логи и трейсы и алерты по золотым сигналам. Сбор метрик в Spring Boot — на странице [Actuator и Micrometer](../spring/spring-actuator.md).

## Метрики, логи и трейсы { #telemetry }

### Что такое observability? { #observability }

**Уровень:** Middle

!!! abstract "Ответ вслух"
    Observability (наблюдаемость) — способность понять, что происходит в проде, не заходя на серверы. Три столпа: метрики — сколько и как часто, логи — что произошло, трейсы — где именно затык на пути запроса через сервисы. Алерты строят по симптомам для пользователя — четырём золотым сигналам: latency, traffic, errors, saturation.

Когда прод падает, нельзя зайти по SSH на каждый сервер и читать логи глазами. Нужны инструменты расследования:

- **Metrics** — числовые агрегаты во времени: QPS, latency (**p50/p95/p99**, не среднее), error rate, CPU и память, глубина очередей. Например: сколько памяти занято в Heap, сколько активных соединений в HikariCP, какой процент ответов API — 500. Стек — Prometheus + Grafana.
- **Logs** — что произошло, текстовые записи событий. В распределённой системе логи **структурированные** (JSON) и централизованные: ELK/EFK (Elasticsearch + Logstash или Fluentd + Kibana) или Loki. Иначе логи 30 сервисов бесполезны.
- **Traces** — где именно: путь запроса через сервисы. **Trace id** протаскивается через все вызовы, а каждый участок — span с таймингом; OpenTelemetry, Jaeger, Zipkin. Отвечает на вопрос «запрос прошёл 8 сервисов — где затык?».

Чтобы найти все логи одного запроса через 5 микросервисов, `traceId` кладут в MDC логгера — он попадает в каждую строку лога. Метрики в Spring Boot собирает Micrometer через Actuator — это разобрано в [Actuator и Micrometer](../spring/spring-actuator.md).

!!! warning "Ловушка: алерт на каждую мелочь"
    Если алертить по каждому всплеску CPU, дежурные привыкают игнорировать уведомления (alert fatigue) и пропускают настоящий сбой. Алерты строят по симптомам для пользователя — **четырём золотым сигналам Google SRE**: latency, traffic, errors, saturation. Мониторинг этих четырёх покрывает большинство проблем.

    2. Как найти все логи одного запроса, прошедшего через несколько сервисов?
    3. Что такое четыре золотых сигнала?
