# Архитектура и микросервисы

## Domain-Driven Design (DDD)

### 1. Ubiquitous Language (Единый язык)

Фундамент DDD: бизнес (продакты, аналитики) и разработчики говорят на одном языке.

- **Антипаттерн:** Бизнес говорит "отгрузка", в базе таблица `delivery`, в коде класс `ShippingManager`. Путаница.
- **По DDD:** Бизнес говорит "Накладная" (Waybill) → класс `Waybill`, таблица `waybill`, переменные `waybill`. Никаких технических синонимов. Код читается как бизнес-спецификация.

### 2. Bounded Contexts (Ограниченные контексты)

Одна сущность значит разное в разных отделах.

**Товар (Product):**
- В контексте **Склада (Inventory)** — габариты, вес, полка, штрихкод.
- В контексте **Продаж (Sales)** — цена, скидка, описание, картинка.

Вместо гигантского `Product` на 100 полей (God Object) — бьём систему на Bounded Contexts. В каждом своя маленькая изолированная модель `Product`. На уровне архитектуры контексты часто становятся отдельными микросервисами.

### 3. Aggregates и Entities

**Entity** — объект с уникальным ID. Свойства меняются, но он остаётся собой (Клиент).

**Aggregate** — группа сущностей, изменяемых как единое целое (транзакция).

```java
// Order — Aggregate Root. Работа с позициями ТОЛЬКО через корень.
public class Order {
    private final OrderId id;
    private final List<OrderItem> items = new ArrayList<>();
    private Money total;

    // ❌ Нельзя менять OrderItem в обход Order — иначе total не пересчитается
    // ✅ Только через метод корня
    public void addItem(Product product, int quantity) {
        OrderItem item = new OrderItem(product, quantity);
        items.add(item);
        recalculateTotal(); // инвариант агрегата сохранён
    }

    private void recalculateTotal() {
        this.total = items.stream()
            .map(OrderItem::subtotal)
            .reduce(Money.ZERO, Money::add);
    }
}
```

`Order` — **Aggregate Root**. На уровне БД это гарантия, что транзакция охватит весь агрегат целиком.

### 4. Value Objects (Объекты-значения)

Объекты **без ID** и **неизменяемые**. Две сущности равны если равны их значения.

```java
// ❌ Просто BigDecimal — нет защиты от ошибок
private BigDecimal amount;

// ✅ Value Object — record идеально подходит (Java 16+)
public record Money(BigDecimal amount, Currency currency) {

    public static final Money ZERO = new Money(BigDecimal.ZERO, Currency.getInstance("KZT"));

    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Нельзя складывать разные валюты");
            // тенге + доллары не сложатся — класс не даст ошибиться
        }
        return new Money(this.amount.add(other.amount), this.currency);
    }
}
```

Купюра 1000 тенге у тебя и у меня равны — серийный номер (ID) не важен, важен номинал.

### 5. Domain Events (Доменные события)

Когда внутри агрегата происходит что-то важное для бизнеса — генерируется событие в прошедшем времени.

```java
// Заказ оплачен → агрегат генерирует событие
public class Order {
    public void markPaid() {
        this.status = OrderStatus.PAID;
        registerEvent(new OrderPaidEvent(this.id, this.total));
    }
}

// Другие Bounded Contexts реагируют:
// - Shipping ловит OrderPaidEvent → собирает посылку
// - Analytics ловит то же событие → строит графики
// Модуль заказов НИЧЕГО не знает о модуле доставки — жёсткая развязка
```

## Паттерны микросервисов

### 1. Circuit Breaker (Предохранитель)

Твой сервис дёргает API банка. Банк завис, отвечает по 10 секунд. Потоки забиваются ожиданием → твой сервис тоже умирает. Это **каскадный сбой**.

```
Closed (закрыт)    → всё хорошо, запросы идут в банк
     ↓ (50% таймаутов за минуту)
Open (открыт)      → "выбило". Запросы не идут, сразу Fallback/ошибка (Fail Fast)
     ↓ (через время)
Half-Open          → пропускает пару тестовых запросов
     ↓ успех → Closed | провал → Open
```

```java
// Resilience4j — стандарт де-факто в Java
@CircuitBreaker(name = "bankApi", fallbackMethod = "fallbackBonus")
public BonusResult calculateBonus(Long userId) {
    return bankApiClient.getBonus(userId); // может зависнуть
}

// Fallback — когда предохранитель открыт
public BonusResult fallbackBonus(Long userId, Throwable t) {
    log.warn("Банк недоступен, возвращаем дефолт", t);
    return BonusResult.empty();
}
```

### 2. Retry (Повтор)

Сбой временный (моргнула сеть) — повторить. Но не просто `for`:

```java
@Retry(name = "bankApi")
// application.yml:
// resilience4j.retry.bankApi.max-attempts: 4
// resilience4j.retry.bankApi.wait-duration: 1s
// resilience4j.retry.bankApi.exponential-backoff-multiplier: 2
```

!!! warning "Два критичных понятия"
    **Exponential Backoff** — интервалы растут (1с, 2с, 4с, 8с). Нельзя долбить упавший сервис каждую миллисекунду.

    **Jitter** — добавление случайности к интервалу. Если 100 инстансов ретрайнут ровно через 2 секунды — устроят DDoS и снова положат сервис.

    При любых ретраях принимающая сторона **обязана** быть идемпотентной, иначе спишем деньги дважды.

### 3. Bulkhead (Переборки)

Термин из кораблестроения: трюм пробило → переборки закрываются → вода не затопит весь корабль.

```
❌ Один общий пул потоков:
   Сервис А (тормозит) сожрал все потоки → к быстрому Сервису Б не сходить

✅ Изолированные пулы:
   [Пул для банка]   ← забился, ну и ладно
   [Пул для склада]  ← жив, ERP продолжает работать
```

Выделяем разные изолированные пулы потоков (или семафоры) для разных интеграций.

### 4. Sidecar (Коляска мотоцикла)

Паттерн деплоя в Kubernetes. Твой сервис — мотоцикл (бизнес-логика). Логирование, метрики, проксирование — в "коляску" (отдельный контейнер в том же поде).

```
┌─────────── Pod ───────────┐
│  [Java App]   [Sidecar]   │
│   пишет в      Fluentbit   │
│   stdout    →  собирает    │
│                → ElasticSearch
└───────────────────────────┘
```

Делят локальную сеть и диск, но изолированы по процессам. Java не тащит тяжёлые библиотеки логирования в свой чистый код.

### 5. API Gateway и BFF

**API Gateway** — единая точка входа: маршрутизация, проверка JWT, rate limiting.

**BFF (Backend For Frontend)** — эволюция Gateway. Отдельный лёгкий сервис под нужды конкретного клиента (один BFF для веба, другой для мобилки). Идёт в разные микросервисы, агрегирует данные, отдаёт фронтендеру одну готовую JSON-ку для конкретного экрана.

```
Без BFF:  Frontend → 10 запросов к складу, биллингу, профилю → сам собирает страницу
С BFF:    Frontend → 1 запрос к BFF → BFF собирает всё → готовый JSON для экрана
```

## Архитектурные стили

### Проблема слоистой архитектуры

`Controller → Service → Repository` — привычно, но содержит бомбу: **направление зависимостей**.

```
Service (бизнес-логика) → знает про → Repository → завязан на → PostgreSQL + Hibernate

Итог: чистая бизнес-логика зависит от инфраструктуры.
Поменять БД / обновить Hibernate / написать unit-тест на расчёт скидки
→ тащишь всю инфраструктуру (поднимаешь Spring-контекст, базу).
```

Для CRUD — ок. Для сложной ERP — смерть.

### Решение: Dependency Inversion

Hexagonal, Onion, Clean Architecture переворачивают игру:

!!! tip "Главное правило"
    Внешние слои (БД, UI, API) зависят от внутренних (бизнес-логика). Внутренние **ничего не знают** о внешних.

Бизнес-логика (Domain) — в центре. Чистое ядро на чистой Java, без аннотаций Spring/Kafka/Hibernate.

### Гексагональная архитектура (Ports and Adapters)

```
            [REST Controller]  [Kafka Listener]   ← Driving Adapters
                    │                 │
                    ▼                 ▼
            ┌───────────────────────────────┐
            │  Driving Port (CreateOrderUseCase) │
            │  ┌─────────────────────────┐  │
            │  │      DOMAIN (ядро)       │  │   ← чистая Java
            │  │   Агрегаты, бизнес-логика │  │
            │  └─────────────────────────┘  │
            │  Driven Port (OrderRepository)  │
            └───────────────────────────────┘
                    │                 │
                    ▼                 ▼
            [Postgres Adapter]  [Bank API Adapter]  ← Driven Adapters
```

**Порты (Java-интерфейсы, внутри домена):**
- **Driving Ports (входящие)** — как мир вызывает домен. `CreateOrderUseCase`.
- **Driven Ports (исходящие)** — как домен обращается к миру. `OrderRepository`. "Мне нужно сохранить заказ, вот контракт. Кто и как — плевать."

**Адаптеры (классы-реализации, снаружи):**
- **Driving Adapters** — `OrderRestController`: принимает JSON, вызывает `CreateOrderUseCase`.
- **Driven Adapters** — `PostgresOrderRepository`: реализует `OrderRepository`, мапит домен в Hibernate `@Entity`.

**Onion и Clean Architecture** делают то же самое, рисуют концентрическими кругами: "Зависимости указывают только внутрь".

### Когда что применять

| | **Layered** | **Hexagonal / Clean** |
|---|---|---|
| **Когда** | Примитивная логика, CRUD | Сложный домен (ERP, статусы, расчёты) |
| **Плюс** | Просто, быстро написать | Тесты бизнес-правил за миллисекунды (мокаем порты) |
| **Минус** | Бизнес-логика зависит от инфраструктуры | Оверинжиниринг для простого CRUD |

!!! tip "Главный плюс Hexagonal"
    Сейчас вызов через REST-контроллер. Завтра бизнес скажет "слушаем события из Kafka" — пишешь новый входящий адаптер (Kafka Listener), дёргающий тот же порт `CreateOrderUseCase`. **Домен не меняется.**

## CQRS и Event Sourcing

### CQRS (Command Query Responsibility Segregation)

**Проблема:** В CRUD одна модель и для записи, и для чтения. Но это разные процессы:

- **Запись (Command)** — сложные проверки, транзакции, блокировки (не продать товар дважды).
- **Чтение (Query)** — сложные дашборды с джойнами 10 таблиц. База тормозит.

**Решение — разделить:**

```
Command (меняет состояние)          Query (только читает)
Create/Update/Delete                Read
Возвращает ID/статус                Возвращает данные
Строгая нормализованная модель      Плоские денормализованные таблицы
        │                                    ▲
        ▼                                    │
   PostgreSQL (Write) ──→ Kafka ──→ Worker ──→ Read-таблица / ElasticSearch
```

Команда валидирует бизнес-правила, сохраняет в PostgreSQL, кидает событие в Kafka. Воркер слушает Kafka, обновляет "таблицу для чтения" или кладёт в ElasticSearch для быстрого поиска.

### Eventual Consistency

!!! warning "Главный подвох CQRS"
    Пишем в одну базу, читаем из другой (через Kafka) → возникает **задержка (lag)**.

    Пользователь нажал "Оплатить". Команда отработала, Write-база обновлена. Но событие в Kafka ещё летит (миллисекунды). Фронтенд запрашивает статус из Read-базы → счёт ещё не оплачен.

    Это **Eventual Consistency** — данные станут консистентными... когда-нибудь (обычно через долю секунды).

### Event Sourcing

Если CQRS — разделение чтения/записи, то Event Sourcing — радикальный подход к тому, **как хранить данные при записи**.

```
Классический подход (хранит ТЕКУЩЕЕ состояние):
   balance = 5000  →  потратили 1000  →  перезаписали: balance = 4000
   Предыдущее состояние потеряно

Event Sourcing (хранит ИСТОРИЮ событий, append-only):
   1. AccountCreatedEvent  (id=1, balance=0)
   2. MoneyDepositedEvent  (id=1, amount=5000)
   3. MoneyWithdrawnEvent   (id=1, amount=1000)

   Текущий баланс = replay всех событий: 0 + 5000 - 1000 = 4000
```

**Плюсы (для ERP):**
- **100% Аудит** — идеально для бухгалтерии, финтеха. История не врёт, событие удалить нельзя.
- **Машина времени** — восстановить состояние на любую секунду прошлого (не проигрывать события после даты).
- **Идеально с CQRS** — Write-модель это Event Store, событие летит в Kafka и обновляет Read-модели.

**Минусы:**
- **Высокий порог входа** — команда должна мыслить событиями.
- **Версионирование событий** — что если через год в `OrderCreated` появилось новое обязательное поле, а в старых событиях его нет? (классический вопрос со звёздочкой — решается через upcasting событий).
- **Eventual Consistency** — тот самый рассинхрон.

## Итоговая шпаргалка

| **Тема** | **Запомнить** |
|---|---|
| **Ubiquitous Language** | Бизнес-термин = класс = таблица. Код читается как спецификация |
| **Bounded Context** | Одна сущность — разные модели в разных контекстах. Часто = микросервис |
| **Aggregate Root** | Изменения только через корень (`order.addItem()`). Защита инвариантов |
| **Value Object** | Без ID, неизменяемый. `Money`, `record`. Защита от ошибок валидации |
| **Domain Event** | Событие в прошедшем времени. Развязывает Bounded Contexts через Kafka |
| **Circuit Breaker** | Closed → Open → Half-Open. Resilience4j. Спасает от каскадного сбоя |
| **Retry** | Exponential Backoff + Jitter. Принимающая сторона идемпотентна |
| **Bulkhead** | Изолированные пулы потоков. Упал банк → склад работает |
| **Sidecar** | Логи/метрики в отдельном контейнере пода, не в Java-коде |
| **API Gateway / BFF** | Gateway — единая точка входа. BFF — готовый JSON под конкретный экран |
| **Hexagonal** | Порты (интерфейсы в домене) + Адаптеры (реализации снаружи). Домен чист |
| **CQRS** | Разделить Command (запись) и Query (чтение). Разные модели |
| **Eventual Consistency** | Write и Read базы рассинхронизированы на доли секунды |
| **Event Sourcing** | Хранить историю событий, не текущее состояние. Replay для состояния |
