# Java Basics

## JVM, JRE, JDK

### 1. JVM (Java Virtual Machine) — Сердце Java

JVM — это виртуальная машина, та самая программа, которая непосредственно выполняет наш Java-код.

- **Как это работает:** Ты пишешь код на Java (`.java`), компилятор превращает его в промежуточный байт-код (`.class`). JVM берет этот байт-код и переводит его в машинный код, понятный конкретной операционной системе (Windows, Linux, macOS).
- **Главная фишка:** Именно JVM обеспечивает знаменитый принцип Java: _"Write Once, Run Anywhere"_ (Написал один раз, запускай где угодно).
- **Важный нюанс:** Сам байт-код платформонезависим, а вот **JVM — платформозависима**. Для каждой ОС нужна своя версия JVM.
- **Что внутри (кратко):**
    - **Classloader:** загружает классы в память.
    - **Memory Area:** управляет памятью (здесь живут Heap, Stack, Metaspace).
    - **Execution Engine:** выполняет код (здесь работают Интерпретатор, JIT-компилятор для оптимизации "горячего" кода и наш любимый Garbage Collector, который чистит память).

### 2. JRE (Java Runtime Environment) — Среда выполнения

JRE — это минимальный пакет, необходимый исключительно для **запуска** уже написанных и скомпилированных Java-приложений.

- **Из чего состоит:** **JRE = JVM + Core Libraries (базовые библиотеки).**
- **Зачем нужны библиотеки:** Сама по себе JVM только выполняет инструкции. Чтобы твое приложение могло работать с файлами, сетью, коллекциями (все эти `java.lang`, `java.util`, `java.io`), ему нужны готовые классы. JRE их предоставляет.
- **Кому это нужно:** Обычным пользователям или серверам, на которых приложение просто должно работать (хотя сейчас чаще используют урезанные кастомные образы, но концептуально это так). Писать код, имея только JRE, ты не сможешь — там нет компилятора.

### 3. JDK (Java Development Kit) — Инструментарий разработчика

JDK — это полный набор инструментов, необходимый нам с тобой для **разработки** программного обеспечения на Java.

- **Из чего состоит:** **JDK = JRE + Development Tools (утилиты для разработки).**
- **Что за утилиты:**
    - `javac` (компилятор, который делает байт-код из твоего текста),
    - `java` (запускатор),
    - `jdb` (дебаггер для поиска багов),
    - `javadoc` (генератор документации) и множество других профилировщиков и анализаторов.
- **Кому это нужно:** Разработчикам. Когда мы ставим Java на свой рабочий компьютер, мы всегда скачиваем именно JDK.

## Garbage Collector

### 1. В чем суть Garbage Collector?

В языках вроде C или C++ программист сам выделяет память и сам должен ее очищать. Забыл очистить — получил утечку памяти (Memory Leak). В Java мы просто создаем объекты (`new Object()`), а JVM сама решает, когда их уничтожить и освободить место. GC — это фоновый процесс, который ищет объекты, которые больше не нужны твоему коду, и удаляет их.

Но как он понимает, что объект больше "не нужен"?

### 2. GC Roots и достижимость объектов

GC не считает ссылки объектов друг на друга, чтобы не попасть в ловушку "циклических ссылок" (когда объект А ссылается на Б, а Б на А, но при этом оба уже не нужны программе).

Вместо этого GC использует алгоритм **Tracing (трассировка)**. Он начинает с так называемых **GC Roots (корней сборки мусора)**. Это "железно" живые объекты:

- Локальные переменные в текущих выполняемых методах (в стеках потоков).
- Статические переменные классов.
- Активные потоки (Threads).

**Правило простое:** GC строит граф ссылок от этих корней. Если до объекта можно добраться по цепочке ссылок от GC Root — он **жив**. Если цепочка оборвалась и до объекта не дойти — он **мусор**, его можно удалять.

### 3. Гипотеза поколений (Weak Generational Hypothesis)

Это фундамент работы большинства сборщиков мусора в Java. Создатели JVM заметили интересную закономерность в поведении программ:

1. **Большинство объектов умирают молодыми.** (Например, переменные внутри цикла или метода — метод отработал, и они больше не нужны).
2. **Те объекты, которые пережили пару сборок мусора, скорее всего, будут жить очень долго.** (Например, кэши, пулы соединений с базой, синглтоны Spring).

Исходя из этого, всю память (Heap — кучу) разделили на регионы, чтобы не сканировать всю память каждый раз.

- **Young Generation (Молодое поколение):** Здесь создаются все новые объекты. Состоит из зоны **Eden** (Эдем) и двух небольших зон **Survivor** (S0 и S1). Когда Eden заполняется, происходит быстрая и легкая сборка мусора — **Minor GC**. Выжившие объекты перекидываются в Survivor.
- **Old Generation / Tenured (Старое поколение):** Сюда попадают объекты-"долгожители", которые пережили несколько циклов Minor GC в молодом поколении. Когда заполняется эта зона, запускается **Major GC (или Full GC)**. Это тяжелая и долгая операция, так как сканируется огромный объем памяти.

### 4. Фазы работы классического GC (Mark-Sweep-Compact)

Когда GC решает навести порядок, он делает три основные вещи:

1. **Mark (Маркировка):** Проходит от GC Roots и ставит "флажок" на всех живых объектах.
2. **Sweep (Очистка):** Проходит по памяти и удаляет все объекты без флажка.
3. **Compact (Сжатие — _опционально, но важно_):** После удаления мусора память становится похожа на швейцарский сыр (фрагментация). GC сдвигает оставшиеся живые объекты в начало памяти, чтобы новые объекты можно было выделять быстро и целым куском.

### 5. Боль всей Java: Stop-The-World (STW)

Это самый важный концепт для понимания архитектуры. Когда GC делает свои основные дела (особенно перемещает объекты в памяти), он **ставит на паузу все потоки твоего приложения**. Это называется **Stop-The-World**. В этот момент твой код замирает, API не отвечает, данные не пишутся.

Вся эволюция сборщиков мусора в Java сводится к одной цели: **сделать эти STW-паузы максимально короткими**, чтобы приложение не "фризило".

### 6. Эволюция сборщиков

- **Serial GC:** Однопоточный. Подходит только для крошечных приложений.
- **Parallel GC:** Использует несколько потоков для сборки, но всё еще вызывает долгие STW. Долгое время был дефолтным.
- **G1 GC (Garbage-First):** Дефолт начиная с Java 9. Дробит память на множество мелких регионов и чистит сначала те, где больше всего мусора. Отлично балансирует пропускную способность и предсказуемость пауз.
- **ZGC и Shenandoah:** Современные шедевры (доступны в новых версиях Java). Они умудряются делать почти всю работу (включая перемещение объектов) _параллельно_ с работой твоего приложения! Паузы STW у них составляют меньше миллисекунды даже на огромных хипах (терабайты памяти). Идеально для высоконагруженных микросервисов.

## Heap & Stack

### 1. Stack (Стек) — Личный рабочий стол потока

Стек — это очень быстрая, но небольшая область памяти. Самое главное правило: **у каждого потока (Thread) в Java есть свой собственный Стек**. Потоки не могут "заглядывать" в стеки друг друга.

- **Как это работает:** Стек работает по принципу LIFO (Last-In, First-Out / Последним пришел — первым ушел). Представь стопку тарелок: ты кладешь тарелку сверху и берешь всегда только верхнюю.
- **Что внутри (Frames):** Когда ты вызываешь метод, в стеке создается новый "фрейм" (кадр). В этом фрейме хранятся:
    - Локальные переменные этого метода.
    - Примитивные типы данных (`int`, `double`, `boolean`, `char` и т.д.).
    - **Ссылки** на объекты (сами объекты здесь не живут, только "адреса", где их найти).
- **Жизненный цикл:** Метод отработал — его фрейм мгновенно удаляется из стека (тарелка снимается). Память очищается сама, без всякого Garbage Collector.
- **Главная ошибка:** Если методы будут вызывать друг друга бесконечно (например, рекурсия без выхода), стопка тарелок упрется в потолок. Ты получишь знаменитую ошибку `StackOverflowError`.

### 2. Heap (Куча) — Общий склад компании

Куча — это огромная область памяти, которая выделяется приложению при запуске. Главное правило: **Куча одна на всё приложение, и все потоки имеют к ней доступ**.

- **Что внутри:** Здесь живут **все объекты** (экземпляры классов, созданные через `new`, массивы, строки).
- **Связь со Стеком:** Когда ты пишешь `User user = new User();`, в Стеке создается локальная переменная `user` (ссылка/адрес), а в Куче выделяется место под сам тяжеловесный объект `User`. Ссылка из Стека указывает на объект в Куче.
- **Жизненный цикл:** Объекты живут здесь до тех пор, пока на них есть хотя бы одна ссылка из Стека (те самые GC Roots, о которых мы говорили). Как только ссылки пропадают, приходит Garbage Collector и вычищает мусор.
- **Главная ошибка:** Если ты создаешь слишком много объектов и не отпускаешь ссылки на них (например, складываешь всё в бесконечный `List`), место на складе закончится. Ты получишь `OutOfMemoryError: Java heap space`.

| **Характеристика** | **Stack (Стек)** | **Heap (Куча)** |
|---|---|---|
| **Доступ** | Локальный (только для одного потока) | Глобальный (общий для всех потоков) |
| **Что хранится** | Примитивы, ссылки, вызовы методов | Сами объекты, JRE классы |
| **Управление** | Автоматически (ОС/JVM при вызове методов) | Garbage Collector |
| **Скорость** | Очень быстрая | Медленнее (требует поиска места и работы GC) |
| **Размер** | Маленький (задается флагом `-Xss`) | Большой (задается флагами `-Xms` и `-Xmx`) |

## Metaspace

Раньше мы говорили, что объекты живут в Куче (Heap), а локальные переменные и вызовы методов — в Стеке (Stack). Но где JVM хранит информацию о самих классах (их структуру, методы, имена полей)? Для этого существует **Metaspace**.

### 1. Что такое Metaspace и где он находится?

Главное отличие Metaspace от Кучи в том, что он находится **вне кучи (Off-Heap)**.

- **Где он физически:** Metaspace использует так называемую _Native Memory_ (нативную память). Это оперативная память (RAM) твоего сервера/компьютера, которую операционная система выделяет процессу JVM напрямую.
- **Что там хранится:** Метаданные классов. Это "чертежи" твоих объектов: структура класса, байт-код его методов, данные JIT-компилятора и другая служебная информация, необходимая JVM для работы.

### 2. Исторический контекст: Убийство PermGen (Вопрос с собеседования)

Интервьюер почти со 100% вероятностью спросит: _"А что было до Metaspace и почему это изменили в Java 8?"_

- **До Java 8:** Эта область памяти называлась **PermGen** (Permanent Generation). Она находилась _внутри_ памяти JVM и имела жестко заданный максимальный размер. Если приложение динамически создавало много классов (что постоянно делают фреймворки вроде Spring или Hibernate через проксирование), память PermGen переполнялась, и приложение насмерть падало с ошибкой `OutOfMemoryError: PermGen space`.
- **С Java 8:** PermGen полностью удалили и заменили на Metaspace. Главная фишка Metaspace в том, что по умолчанию он **динамически растет** и ограничен только общим объемом оперативной памяти твоего сервера. Ошибка `OOM: PermGen` ушла в прошлое.

### 3. Ловушка для сеньора: Где теперь живут статические переменные?

Это самый каверзный вопрос по этой теме.

Многие разработчики по старой памяти из книжек по Java 7 отвечают, что статические переменные и String Pool хранятся в Metaspace (или PermGen). **Это грубая ошибка!**

- **String Pool** переехал в основную Кучу (Heap) еще в Java 7.
- **Статические переменные** (и сами объекты типа `java.lang.Class`) переехали из PermGen в основную Кучу (Heap) в Java 8.

В Metaspace осталась _только_ чистая метаинформация и байт-код для JVM.

### 4. Как Metaspace очищается (Garbage Collection)?

Хотя Metaspace может резиново растягиваться, он не бесконечен. Как оттуда удаляется мусор?

Метаданные класса живут в Metaspace до тех пор, пока жив его **ClassLoader** (Загрузчик классов).

- В обычном приложении базовые классы живут от старта до остановки сервера.
- Но если ты используешь "горячую замену" кода (Hot Reload) или сложные архитектуры серверов приложений (Tomcat), старые `ClassLoader`-ы уничтожаются вместе со своими классами, и тогда Garbage Collector приходит в Metaspace и освобождает нативную память.

!!! tip "Практический совет (Best Practice)"
    В production-среде (особенно в облаках вроде Kubernetes, где память жестко лимитирована) всегда нужно ограничивать рост Metaspace специальным флагом (например, `-XX:MaxMetaspaceSize=256m`). Иначе при утечке классов Metaspace может сожрать всю RAM сервера, и операционная система просто "убьет" твой контейнер (сработает OOM Killer).

## OOM

### 1. Что вообще такое OOM?

Первое и самое важное правило для собеседования: **OOM — это не Exception, это Error**. Он наследуется от `java.lang.VirtualMachineError`. Это значит, что JVM сигнализирует о критической ситуации: память закончилась, Garbage Collector (GC) сделал всё что мог, но не смог освободить место для нового объекта. Ловить его через `try-catch` — плохая практика (хоть технически и возможная), потому что приложение уже находится в нестабильном состоянии.

### 2. Основные виды OOM (Почему он падает)

На собеседовании не говори просто "закончилась память". Память бывает разная. Вот основные варианты, с которыми ты столкнешься на практике:

| Тип ошибки | Суть проблемы | Частая причина в коде |
|---|---|---|
| **Java heap space** | Классика. В Куче (Heap) нет места для создания нового объекта. | Утечка памяти (коллекция бесконечно растет), попытка выгрузить огромный файл или `SELECT *` из БД в память. |
| **GC overhead limit exceeded** | Приложение "буксует". GC работает более 98% времени, но освобождает менее 2% памяти. | Выделяется слишком много временных объектов, GC постоянно работает, но не успевает их чистить. |
| **Metaspace** | Переполнилась область памяти, где JVM хранит метаданные классов. | Баги с динамической генерацией классов (часто грешат фреймворки типа Spring/Hibernate при кривой настройке). |
| **Unable to create new native thread** | JVM не может создать новый поток на уровне операционной системы. | Лимит ОС на количество потоков исчерпан, либо закончилась физическая оперативная память на сервере. |

### 3. Как обнаружить и расследовать OOM?

Обычно OOM обнаруживается сам — приложение просто умирает с ошибкой в логах. Твоя задача как инженера — понять, **почему** это произошло.

- **JVM Флаги (Must-have):** Ты обязан знать флаг `-XX:+HeapDumpOnOutOfMemoryError`. Если добавить его при запуске приложения, JVM в момент падения от OOM автоматически создаст файл-слепок памяти (Heap Dump). Также полезен флаг `-XX:HeapDumpPath=...`, чтобы указать, куда этот файл сохранить.
- **Мониторинг (Grafana/Prometheus):** В реальной жизни мы смотрим на графики. Если график использования памяти плавно ползет вверх днями и неделями, не падая после сборок мусора — это 100% утечка памяти (Memory Leak). Если график взлетел вертикально вверх за секунду — это резкий спайк трафика или кривой запрос к БД.
- **JMX и Профилировщики:** Использование утилит вроде VisualVM или JProfiler, чтобы подключиться к работающей JVM в реальном времени и посмотреть, какие объекты занимают место.

### 4. Как лечить OOM?

Интервьюеры обожают вопрос: "У тебя упал OOM, твои действия?". Никогда не отвечай: "Я просто увеличу память (флаг `-Xmx`)". Это костыль, который лишь отсрочит следующее падение, если в коде утечка.

Вот правильный алгоритм Senior-разработчика:

1. **Собрать данные:** Забрать тот самый Heap Dump, который сгенерировала JVM при падении.
2. **Провести анализ:** Открыть дамп в специальной программе (золотой стандарт — **Eclipse MAT** — Memory Analyzer Tool).
3. **Найти виновника:** В MAT есть функция _Dominator Tree_ или _Leak Suspects Report_. Инструмент сам покажет тебе: "Вот этот `HashMap` держит 80% всей памяти, а внутри него лежат миллионы объектов `User`".
4. **Пофиксить код:**
    - Если это утечка: найти, где мы складываем объекты в кэш/коллекцию и забываем их оттуда удалять.
    - Если это спайк данных: переписать запрос к БД на использование пагинации (вытягивать батчами по 1000 строк, а не миллион за раз), использовать потоковое чтение файлов (Stream API, `BufferedReader`), а не грузить файл в `byte[]` целиком.
5. **Оптимизировать JVM:** И вот только если анализ показал, что утечек нет, а приложению просто реально нужно больше памяти для нормальной работы возросшей нагрузки, мы аккуратно увеличиваем `-Xmx`.

## Примитивные типы данных vs Ссылочные типы

В Java существует четкое разделение на примитивные (8 штук) и ссылочные типы данных (объекты, массивы, интерфейсы, `enum`).

### 1. Примитивные типы (Primitives)

Они встроены в язык, не являются объектами (у них нет методов) и максимально оптимизированы для скорости.

| **Категория** | **Тип** | **Размер в памяти** | **Значение по умолчанию** |
|---|---|---|---|
| **Целочисленные** | `byte` | 1 байт (8 бит) | 0 |
| | `short` | 2 байта (16 бит) | 0 |
| | `int` | 4 байта (32 бита) | 0 |
| | `long` | 8 байт (64 бита) | 0L |
| **С плавающей точкой** | `float` | 4 байта (32 бита) | 0.0f |
| | `double` | 8 байт (64 бита) | 0.0d |
| **Символьный** | `char` | 2 байта (16 бит) | `\u0000` |
| **Логический** | `boolean` | Зависит от JVM | `false` |

### 2. Главные отличия

1. **Расположение в памяти:**
    - **Примитивы:** Хранят само значение. Локальные переменные-примитивы всегда создаются в **Стеке (Stack)** потока. _(Исключение: если примитив является полем класса, он будет храниться в Куче вместе с самим объектом)._
    - **Ссылочные:** Хранят **ссылку (адрес памяти)** на объект. Сама ссылка лежит в Стеке, а тяжеловесный объект, на который она указывает, всегда лежит в **Куче (Heap)**.
2. **Возможность быть `null`:**
    - Примитивы **не могут** быть `null`. У них всегда есть значение по умолчанию.
    - Ссылочные типы могут указывать в никуда (иметь значение `null`), что часто приводит к `NullPointerException`.
3. **Производительность:**
    - Доступ к примитивам быстрее, так как не нужно "бегать" по ссылкам из Стека в Кучу. Кроме того, массивы примитивов лежат в памяти сплошным куском, что идеально для кэша процессора (Cache Locality).

### 3. Классическая ловушка: Передача в методы

Это один из самых частых вопросов-ловушек.

!!! warning "Золотое правило Java"
    В Java **ВСЁ** передается исключительно **по значению** (pass-by-value). Никакой передачи "по ссылке" в стиле C++ здесь нет.

- **При передаче примитива:** в метод копируется само его значение (например, число `5`). Изменения внутри метода никак не затронут оригинальную переменную.
- **При передаче объекта:** в метод копируется **значение ссылки** (адрес в памяти).
    - Если внутри метода изменить состояние объекта (например, `user.setName("John")`), то оригинал **изменится**, так как обе ссылки (оригинальная и скопированная) указывают на один и тот же объект в Куче.
    - Если внутри метода присвоить ссылке новый объект (`user = new User()`), оригинал **НЕ изменится**, так как ты просто переопределил локальную копию адреса, а не сам исходный объект.

## Автоупаковка (Autoboxing) и Распаковка (Unboxing)

В Java исторически сложилось две системы типов: быстрые примитивы (`int`, `boolean`) и тяжеловесные объекты. Но коллекции (например, `ArrayList`) и Generics умеют работать **только с объектами**. Чтобы подружить эти два мира, в Java 5 добавили классы-обертки (Wrapper classes: `Integer`, `Double`, `Boolean` и т.д.) и механизм автоматического преобразования между ними.

### 1. Как это работает под капотом

Компилятор делает всю грязную работу за нас, подставляя нужные методы на этапе компиляции:

- **Autoboxing (Автоупаковка):** Преобразование примитива в объект-обертку.
    - **Ты пишешь:** `Integer num = 10;`
    - **Компилятор делает:** `Integer num = Integer.valueOf(10);`
- **Unboxing (Распаковка):** Преобразование объекта-обертки обратно в примитив.
    - **Ты пишешь:** `int a = num;`
    - **Компилятор делает:** `int a = num.intValue();`

### 2. Главные подводные камни (Ловушки с собеседований)

Это именно то, что нужно знать для успешного прохождения технического скрининга. Здесь кроются три главные проблемы:

**Ловушка №1: Скрытый `NullPointerException` (NPE)** — Примитивы не могут быть `null`, а объекты-обертки — могут. Если попытаться распаковать `null`, приложение упадет.

```java
Integer wrapper = null;
int primitive = wrapper; // Ошибка в рантайме! Под капотом вызовется null.intValue(), что даст NPE.
```

**Ловушка №2: Кэширование целых чисел (Integer Cache)** — Это классический вопрос на понимание того, как работает оператор `==` со ссылочными типами. В целях экономии памяти JVM кэширует объекты-обертки для небольших значений: от **-128 до 127** (этот диапазон можно увеличить флагами JVM, но по умолчанию он такой).

```java
Integer a = 100;
Integer b = 100;
System.out.println(a == b); // true. Оба указывают на один и тот же объект в кэше.

Integer c = 200;
Integer d = 200;
System.out.println(c == d); // false. Значение 200 не кэшируется, в Куче (Heap) создаются два разных объекта.
```

!!! note "Правило"
    Никогда не сравнивай классы-обертки через `==`. Всегда используй метод `.equals()`.

**Ловушка №3: Удар по производительности и памяти** — Поскольку компилятор делает упаковку незаметно, очень легко написать код, который будет незаметно создавать миллионы объектов в цикле, забивая Heap и заставляя Garbage Collector работать на износ.

```java
Long sum = 0L; // Объект-обертка
for (long i = 0; i < Integer.MAX_VALUE; i++) {
    sum += i; // Здесь на каждой итерации происходит распаковка, сложение и создание НОВОГО объекта Long!
}
```

_Решение:_ Использовать `long sum = 0L;` (примитив), чтобы избежать ненужного создания объектов.

## Контракт `equals()` и `hashCode()`

В базовом классе `Object` (от которого наследуются все классы в Java) уже есть эти два метода. По умолчанию `equals()` работает точно так же, как оператор `==` (сравнивает ссылки в памяти), а `hashCode()` возвращает число, сгенерированное на основе адреса объекта в памяти.

Но для бизнес-логики нам нужно сравнивать объекты по их содержимому (полям), поэтому мы их переопределяем. И вот тут вступает в силу жесткий контракт.

### 1. Четыре правила контракта (Шпаргалка)

1. **Согласованность с `equals`:** Если `a.equals(b) == true`, то их хэш-коды **обязаны** быть одинаковыми (`a.hashCode() == b.hashCode()`).
2. **Коллизии допустимы:** Если `a.hashCode() == b.hashCode()`, то объекты **не обязательно** равны по `equals()`. Такая ситуация называется _коллизией_.
3. **Оптимизация:** Если `a.hashCode() != b.hashCode()`, то объекты **гарантированно не равны** по `equals()`.
4. **Неизменность (Идемпотентность):** Вызов `hashCode()` на одном и том же объекте несколько раз подряд должен возвращать одно и то же число (если поля объекта не менялись).

### 2. Зачем вообще нужен этот контракт? (Суть для собеседования)

Интервьюер обязательно спросит: _"А что будет, если я переопределю `equals`, но забуду переопределить `hashCode`?"_

Чтобы ответить блестяще, нужно объяснить, как под капотом работает `HashMap` (или `HashSet`). Хэш-таблицы созданы для того, чтобы искать элементы с невероятной скоростью — за время O(1).

Представь `HashMap` как шкаф с множеством пронумерованных ящиков (бакетов/корзин):

1. **Поиск ящика (работает `hashCode`):** Когда ты кладешь объект в `HashMap` (`map.put(key, value)`), коллекция берет твой `key`, вызывает у него `hashCode()` и с помощью математической формулы вычисляет номер ящика. Это происходит мгновенно.
2. **Поиск внутри ящика (работает `equals`):** Проблема в том, что размер шкафа ограничен, а вариантов хэш-кодов — 4 миллиарда (`int`). Неизбежно разные объекты попадут в один и тот же ящик (это и есть коллизия). Внутри ящика они выстраиваются в связный список (или в красно-черное дерево). Чтобы найти нужный объект среди соседей по ящику, `HashMap` по очереди вызывает метод `equals()` и сравнивает твой ключ с теми, что уже лежат там.

### 3. Цена ошибки (Что будет, если нарушить контракт)

**Сценарий 1: Забыли `hashCode` (Разные хэш-коды у равных объектов)** — Ты создал двух пользователей с одинаковым ID, именем и почтой. По логике `equals()` они равны. Ты кладешь первого в `HashMap`. Позже ты хочешь достать его данные, используя второго как ключ. _Что произойдет:_ Так как `hashCode` не переопределен, у второго объекта будет _другой_ хэш-код. `HashMap` пойдет искать его **в другой ящик**! Он посмотрит в пустой ящик, вернет `null`, и объект навсегда "потеряется" в памяти. Это прямой путь к утечке памяти (Memory Leak).

**Сценарий 2: Плохой `hashCode` (Например, всегда возвращает 1)** — Контракт не нарушен, но ты решил возвращать константу. _Что произойдет:_ Все объекты пойдут в один-единственный ящик. `HashMap` выродится в обычный связный список. Скорость поиска упадет с мгновенного O(1) до медленного O(N). Сервер начнет жестко тормозить при увеличении данных.

### 4. Как избежать проблем на практике?

- **Никогда не пиши руками:** Всегда генерируй эти методы через IDE (IntelliJ IDEA) или используй Lombok (`@EqualsAndHashCode`).
- **Используй неизменяемые поля:** Хэш-код должен вычисляться только на основе тех полей, которые участвуют в `equals`. Желательно, чтобы эти поля были `final`. Если ты поменяешь поле объекта _после_ того, как положил его в `HashSet`, его хэш-код изменится, и ты больше никогда не сможешь его оттуда достать.
- **Современный подход:** Начиная с Java 14, можно использовать `record`. Там `equals()` и `hashCode()` переопределены идеально и "из коробки" прямо на уровне языка.

## String, StringBuilder и StringBuffer

Вся суть различий между этими тремя классами сводится к двум концепциям: **Изменяемость (Mutability)** и **Потокобезопасность (Thread Safety)**.

### 1. String — Неизменяемый (Immutable)

Объекты класса `String` в Java неизменяемы. Это значит, что после создания строки её содержимое нельзя поменять. Вообще никак.

- **Как это работает:** Когда ты делаешь конкатенацию `String s = "Hello" + " World";` или вызываешь методы вроде `s.replace()`, `s.toUpperCase()`, оригинальная строка **не меняется**. В Куче (Heap) каждый раз создается абсолютно **новый** объект, а старый отправляется на съедение Garbage Collector-у.
- **Зачем так сделали?**
    1. **Безопасность:** Строки часто используются как ключи в `HashMap`, пароли, пути к файлам и URL. Если бы строку можно было изменить из другого места программы, это создало бы гигантские дыры в безопасности.
    2. **Потокобезопасность:** Неизменяемый объект можно смело передавать между любыми потоками, не боясь состояний гонки (Race Conditions).
    3. **Кэширование:** Благодаря неизменяемости стал возможен String Pool (о котором мы поговорим чуть позже).
- **Главная проблема:** Конкатенация в цикле. Если ты склеиваешь тысячи строк через `+` в цикле, ты создаешь тысячи промежуточных "мусорных" объектов, убивая производительность и память.

### 2. StringBuilder — Изменяемый работяга (Mutable)

`StringBuilder` был создан специально для решения проблемы производительности `String`.

- **Как это работает:** Внутри него лежит обычный расширяемый массив (`byte[]` в современных версиях Java). Когда ты вызываешь `append()`, он не создает новый объект, а просто дописывает символы в этот внутренний массив. Если массив заполняется, он пересоздает его, увеличивая размер (по умолчанию в 2 раза + 2), и копирует данные.
- **Где применять:** Везде, где нужно динамически собирать текст. Например, когда ты пишешь логику для форматирования документов, парсинга больших файлов или генерации сложных SQL-запросов, использование `StringBuilder` — это единственный правильный путь.
- **Важный нюанс:** Он **не потокобезопасен**. Если два потока одновременно попытаются сделать `append()`, данные перемешаются или приложение упадет с ошибкой `ArrayIndexOutOfBoundsException`.

### 3. StringBuffer — Потокобезопасный дедушка (Mutable & Synchronized)

`StringBuffer` — это брат-близнец `StringBuilder`, но с одним отличием.

- **Как это работает:** Все его основные методы (например, `append`, `insert`, `delete`) помечены ключевым словом `synchronized`. Это значит, что в один момент времени только один поток может изменять эту строку.
- **Где применять:** Практически **нигде** в современном коде.
- **Почему он устарел:** Синхронизация работает очень медленно. На практике нам крайне редко нужно, чтобы несколько потоков одновременно дописывали что-то в одну и ту же строку. А учитывая, что сейчас в ходу современные архитектуры с виртуальными потоками, блокировки через `synchronized` на уровне конкатенации строк — это огромный антипаттерн. Обычно каждый поток собирает свою строку локально через `StringBuilder`, а потом уже передает готовый `String` дальше.

| **Характеристика** | **String** | **StringBuilder** | **StringBuffer** |
|---|---|---|---|
| **Изменяемость** | Нет (Immutable) | Да (Mutable) | Да (Mutable) |
| **Потокобезопасность** | Да (из-за неизменяемости) | Нет | Да (через `synchronized`) |
| **Производительность** | Медленно (при склеивании) | **Очень быстро** | Медленно (из-за блокировок) |
| **Когда использовать** | Для хранения текста, ключей `Map` | Для сборки текста в одном потоке | Только в легаси-коде (Legacy) |

### Секретный бонус для сеньорского ответа (Оптимизация компилятора)

Интервьюеры любят валить вопросом: _"А что будет, если я напишу `String s = a + b + c;` вне цикла? Обязательно ли тут писать `StringBuilder` руками?"_

**Правильный ответ:** Нет, не обязательно. Начиная с Java 9, компилятор больше не переводит оператор `+` в `StringBuilder` под капотом (как это было в Java 8). Теперь используется механизм `StringConcatFactory` с инструкцией `invokedynamic`. JVM сама на лету решает, как максимально эффективно и быстро склеить эти строки, выделяя ровно столько памяти, сколько нужно, без создания лишних объектов.

Поэтому для простых склеиваний вне циклов обычный `+` сейчас работает даже эффективнее и читается лучше. А вот **внутри циклов** `StringBuilder` всё еще обязателен.

## Пул строк (String Pool) и метод intern()

Поскольку строки (`String`) используются в приложениях повсюду (текст, ключи, пути, настройки), они занимают огромную часть памяти. Чтобы не плодить тысячи одинаковых объектов "User" или "Error" в памяти, разработчики Java придумали хитрый механизм кэширования — **String Pool**.

### 1. Что такое String Pool?

Это специальная область памяти внутри Кучи (Heap). Ее главная задача — хранить **только один экземпляр** каждой уникальной строки, созданной через литерал (в двойных кавычках).

- **Как это работает при создании через литерал:** Когда ты пишешь `String s1 = "Java";`, JVM сначала идет в String Pool и проверяет: _"Есть ли у меня уже строка 'Java'?"_.
    - Если **нет** — она создает новый объект в пуле и возвращает ссылку на него.
    - Если **есть** (например, ты пишешь `String s2 = "Java";` строчкой ниже) — JVM **не создает** новый объект. Она просто возвращает ссылку на уже существующий объект из пула.
    - **Итог:** `s1 == s2` вернет `true`, потому что обе переменные указывают на один и тот же участок памяти.

### 2. Классическая ловушка: Литерал vs Ключевое слово `new`

Это любимый вопрос на скринингах. Что будет, если создать строку через оператор `new`?

```java
String s1 = "Java";               // Идет в пул
String s2 = new String("Java");   // Игнорирует пул для создания объекта
```

Когда ты используешь `new`, ты **принудительно** приказываешь JVM: _"Создай мне абсолютно новый объект в основной Куче (Heap), даже если такая строка уже есть в пуле!"_.

- **Итог:** `s1 == s2` вернет `false`. Ссылки разные. `s1` смотрит в String Pool, а `s2` смотрит в обычный Heap.

!!! note "Золотое правило"
    Никогда не создавай строки через `new String("text")`, если на то нет очень специфической причины. Это пустая трата памяти.

### 3. Магия метода intern()

А что делать, если строка пришла к нам динамически (например, мы прочитали ее из файла, из базы данных или склеили через `StringBuilder`), и мы хотим положить ее в пул для экономии памяти?

Для этого существует метод `intern()`.

- **Как он работает:** Когда ты вызываешь `someString.intern()`, JVM берет содержимое этой строки и идет в String Pool.
    - Если такая строка там **уже есть** — метод возвращает ссылку на объект из пула (а оригинальный динамический объект со временем съест Garbage Collector).
    - Если такой строки там **нет** — JVM добавляет эту строку в пул и возвращает ссылку на нее.

**Пример для понимания:**

```java
String s1 = "Hello";
String s2 = new String("Hello");
String s3 = s2.intern();

System.out.println(s1 == s2); // false (один в пуле, другой в Heap)
System.out.println(s1 == s3); // true (s3 получил ссылку из пула, где уже лежал s1)
```

### 4. Историческая справка (Бонус для сеньорского ответа)

Если на собеседовании заикнутся про "опасность" метода `intern()`, смело выдавай этот факт:

- **До Java 7:** String Pool находился в специальной памяти _PermGen_ (Permanent Generation), которая имела жестко фиксированный размер и **не очищалась** Garbage Collector'ом. Если разработчик активно использовал `intern()`, память быстро забивалась, и приложение падало с ошибкой `OutOfMemoryError: PermGen space`.
- **С Java 7 и выше:** String Pool перенесли в основную часть Кучи (Heap). Теперь Garbage Collector умеет чистить пул от строк, на которые больше нет ссылок в приложении. Использовать `intern()` стало абсолютно безопасно, а PermGen в новых версиях Java (начиная с 8-й) вообще заменили на _Metaspace_.

## Значения по умолчанию и инициализация переменных

В Java поведение переменной критически зависит от того, **где именно** она объявлена: на уровне класса (поля) или внутри метода (локальные переменные).

### 1. Поля класса (Instance & Static variables)

Когда ты создаешь объект через `new`, под него выделяется память в Куче (Heap). JVM заботливо "зачищает" эту память, автоматически присваивая всем полям класса безопасные значения по умолчанию (фактически, забивает память нулями).

Тебе не обязательно их инициализировать руками. Если ты не присвоишь значение, JVM сделает это за тебя:

| **Тип данных** | **Значение по умолчанию** |
|---|---|
| `byte`, `short`, `int`, `long` | `0` (или `0L` для long) |
| `float`, `double` | `0.0f` или `0.0d` |
| `char` | `'\u0000'` (нулевой символ, пустота) |
| `boolean` | `false` |
| **Все ссылочные типы** (String, объекты, массивы) | `null` |

!!! info "Важно"
    Элементы массива (даже если массив создан локально в методе) тоже получают значения по умолчанию, так как сам массив всегда является объектом и создается в Куче. Например, `int[] arr = new int[5];` будет сразу заполнен пятью нулями.

### 2. Локальные переменные (Local variables)

Локальные переменные — это те, которые ты объявляешь **внутри методов**, конструкторов или блоков кода (например, внутри цикла `for`).

Главное правило: **У локальных переменных НЕТ значений по умолчанию.**

Если ты объявишь переменную внутри метода и попытаешься ее использовать (например, вывести в консоль или прибавить к ней число) до того, как присвоишь ей значение, **компилятор выдаст ошибку** (`variable might not have been initialized`), и программа даже не скомпилируется.

```java
public void calculate() {
    int result;
    // System.out.println(result); // Ошибка компиляции!
    result = 10;
    System.out.println(result); // Теперь всё отлично
}
```

### 3. Почему создатели Java сделали именно так? (Ответ для сеньора)

Интервьюер обязательно спросит: _"А почему JVM не может так же заботливо заполнять нулями и локальные переменные?"_

Здесь есть две фундаментальные причины:

1. **Защита от глупых ошибок (Safety):** В языках вроде C или C++ неинициализированная локальная переменная просто берет тот "мусор", который случайно остался в этой ячейке памяти от предыдущих операций. Это приводило к ужасным и трудноуловимым багам. Создатели Java решили жестко бить разработчика по рукам на этапе компиляции, заставляя его явно указывать стартовое значение. Это заставляет писать более осознанный и предсказуемый код.
2. **Производительность (Performance):** Как мы помним, локальные переменные живут в Стеке. Стек работает невероятно быстро: методы постоянно вызываются, их фреймы создаются и уничтожаются миллионы раз в секунду. Если бы JVM тратила время на зануление каждой переменной в Стеке при каждом вызове метода, это нанесло бы колоссальный удар по производительности приложения. Поэтому JVM оставляет эту ответственность разработчику.

## final, finally и finalize()

### 1. `final` (Модификатор) — Печать неизменности

Это ключевое слово, которое запрещает изменения. Его поведение зависит от того, к чему именно ты его применяешь: к переменной, методу или классу.

- **`final` переменная (Константа):** Значение переменной можно задать только один раз.
    - _Ловушка для мидла:_ Если переменная примитивная (`final int x = 5;`), ее значение изменить нельзя. Но если переменная ссылочная (например, `final List<String> list = new ArrayList<>();`), то **нельзя изменить саму ссылку** (присвоить новый `new ArrayList()`), но **можно менять состояние самого объекта** (добавлять и удалять элементы через `list.add()`).
- **`final` метод:** Запрещает переопределение (Override) этого метода в классах-наследниках. Это нужно, когда ты написал критически важную бизнес-логику и хочешь гарантировать, что никто не сломает ее поведение при наследовании.
- **`final` класс:** Запрещает наследование от этого класса. Самый яркий пример из JDK — класс `String`. Никто не может создать `class MyString extends String`, что гарантирует его безопасность и неизменяемость.

### 2. `finally` (Блок кода) — Гарантия выполнения

Это часть конструкции `try-catch-finally` для обработки исключений.

- **Как это работает:** Блок `finally` выполняется **всегда**, независимо от того, выбросилось исключение в блоке `try` или программа отработала успешно. Даже если внутри `try` или `catch` стоит оператор `return`, JVM сначала выполнит блок `finally`, и только потом выйдет из метода.
- **Зачем нужно:** Исторически он использовался для железобетонного закрытия ресурсов: сетевых соединений, потоков ввода-вывода (файлов) или соединений с базой данных.
- **Секрет для сеньора (Когда `finally` НЕ выполнится?):** Интервьюер обязательно спросит об этом. Блок `finally` не отработает только в экстремальных случаях:
    1. Если вызвать `System.exit(0)` внутри `try` или `catch` (это принудительно убивает JVM).
    2. Если произойдет фатальная ошибка на уровне памяти (например, `OutOfMemoryError` или падение самой операционной системы).
    3. Если поток, выполняющий `try`, убьют снаружи.
- **Современный подход:** Начиная с Java 7, для закрытия ресурсов лучше использовать конструкцию **`try-with-resources`**. Она делает то же самое под капотом, но код становится чище, и тебе не нужно писать блок `finally` руками.

### 3. `finalize()` (Метод) — Предсмертная записка объекта

Это метод, определенный в самом главном классе `Object`.

- **Как это задумывалось:** Garbage Collector (сборщик мусора) вызывает этот метод у объекта прямо перед тем, как навсегда удалить его из памяти. Разработчики могли переопределить этот метод, чтобы написать логику "последнего шанса" для закрытия ресурсов.
- **Почему это стало антипаттерном:**
    1. **Непредсказуемость:** Никто не дает гарантий, когда именно GC решит собрать мусор. Метод `finalize()` может вызваться через секунду, через час, или вообще никогда (если программа завершится раньше).
    2. **Падение производительности:** Объекты с переопределенным `finalize()` собираются в разы медленнее. GC приходится ставить их в специальную очередь (Finalization Queue), что сильно тормозит очистку Кучи (Heap).
    3. **Опасность "воскрешения":** Внутри `finalize()` неопытный разработчик мог случайно присвоить ссылку на этот умирающий объект какой-нибудь статической переменной, тем самым "воскресив" его и сломав логику GC.
- **Статус:** Начиная с Java 9 метод официально помечен как `@Deprecated` (устаревший). Использовать его в реальном коде категорически запрещено. Для сложной очистки ресурсов сейчас используют `java.lang.ref.Cleaner`.

| **Понятие** | **Что это такое?** | **Где применяется?** | **Главная суть** |
|---|---|---|---|
| **`final`** | Ключевое слово | Переменные, методы, классы | Запрет на изменения/наследование |
| **`finally`** | Блок кода | Обработка исключений (`try-catch`) | Выполняется всегда (освобождение ресурсов) |
| **`finalize()`** | Метод класса `Object` | Жизненный цикл объекта (Garbage Collector) | Вызывается перед удалением (Устарел!) |

## Ключевое слово static и блоки инициализации

### 1. Суть ключевого слова `static`

Главное правило, которое нужно запомнить: **Всё, что помечено словом `static`, принадлежит самому классу, а не конкретному объекту (экземпляру) этого класса.**

Чтобы обратиться к статическому члену, тебе не нужно создавать объект через `new`. Ты обращаешься к нему напрямую через имя класса (например, `Math.max()`).

### 2. Статические переменные (Поля)

Когда ты объявляешь обычное поле, каждый новый объект получает свою собственную копию этой переменной в Куче (Heap). Но если ты делаешь поле `static`:

- **Общая память:** Оно существует в **единственном экземпляре** для всех объектов этого класса.
- **Где хранится:** Статические переменные вместе с метаданными класса хранятся в специальной области памяти — **Metaspace** (начиная с Java 8, раньше это был PermGen). _(Примечание: сами объекты, на которые ссылаются статические поля, лежат в Heap; в Metaspace — служебная информация.)_
- **Ловушка:** Если один поток изменит значение статической переменной, это изменение мгновенно отразится для всех остальных объектов этого класса в приложении. Именно поэтому статические поля чаще всего делают константами (`public static final`).

### 3. Статические методы

Это методы, которые выполняют логику, не привязанную к состоянию конкретного объекта. Отличный пример — утилитные классы (вроде `StringUtils` или `Math`).

**Два главных ограничения (очень любят спрашивать):**

1. **Нет слова `this` и `super`:** Статический метод не знает, от имени какого объекта его вызвали (ведь объекта может и не быть). Поэтому из статического метода **нельзя** напрямую обратиться к нестатическим полям или методам.
2. **Method Hiding (Сокрытие), а не Переопределение (Override):** Статические методы **нельзя переопределить**. Если в классе-наследнике ты напишешь статический метод с точно таким же названием и аргументами, компилятор не ругнется. Но полиморфизм (позднее связывание) работать не будет. Вызовется тот метод, чей тип ссылки указан при компиляции. Это называется "сокрытием метода".

### 4. Блоки инициализации

Иногда просто присвоить значение переменной при объявлении (`static int x = 5;`) недостаточно. Нужна сложная логика (например, загрузить данные из файла или собрать сложную `Map`). Для этого есть блоки.

- **Статический блок (`static { ... }`):** Выполняется **только один раз** за всё время работы приложения — в тот момент, когда `ClassLoader` загружает этот класс в память (еще до создания каких-либо объектов).
- **Логический / Нестатический блок (`{ ... }`):** Выполняется **каждый раз** при создании нового объекта через `new`, причем _до_ того, как отработает конструктор. Исторически это использовалось, чтобы вынести общую логику из нескольких разных конструкторов, чтобы не дублировать код.

### 5. Секретное оружие для собеса: Порядок инициализации

Это топ-1 задача на скринингах. Тебе дадут класс-наследник с кучей статических и нестатических блоков, полей и конструкторов, и спросят: _"В каком порядке в консоль выведутся сообщения при вызове `new Child()`?"_.

**Вот железобетонный алгоритм (заучить и сохранить):** Когда ты создаешь объект дочернего класса, инициализация всегда идет сверху вниз, от родителя к наследнику, и от статики к динамике:

1. **Статические поля и статические блоки Суперкласса** (Родителя).
2. **Статические поля и статические блоки Подкласса** (Наследника). _(На этом этапе классы загружены в память. Теперь начинается создание самого объекта.)_
3. **Нестатические поля и логические блоки Суперкласса**.
4. **Конструктор Суперкласса**.
5. **Нестатические поля и логические блоки Подкласса**.
6. **Конструктор Подкласса**.

## Перечисления (`Enum`) под капотом

Главное, что нужно сказать на собеседовании: **`enum` — это синтаксический сахар.** На уровне JVM никаких "перечислений" не существует. Есть только обычные классы.

Когда ты пишешь:

```java
public enum Status {
    NEW, IN_PROGRESS, DONE
}
```

Компилятор делает магию и превращает этот код примерно в следующее:

```java
public final class Status extends java.lang.Enum<Status> {
    public static final Status NEW = new Status("NEW", 0);
    public static final Status IN_PROGRESS = new Status("IN_PROGRESS", 1);
    public static final Status DONE = new Status("DONE", 2);

    private Status(String name, int ordinal) {
        super(name, ordinal);
    }
    // ... скрытые методы компилятора ...
}
```

Из этого факта вытекают все жесткие правила и каверзные вопросы с собеседований.

### 1. Главные ограничения (Ловушки)

- **Наследование запрещено:** Так как твой `enum` уже неявно унаследован от класса `java.lang.Enum`, он не может наследоваться ни от чего другого (в Java нет множественного наследования классов).
- **Интерфейсы разрешены:** А вот реализовывать (`implements`) сколько угодно интерфейсов `enum` может. Это часто используют, чтобы связать разные перечисления общим контрактом поведения.
- **Конструктор всегда `private`:** Ты не можешь создать новый экземпляр `enum` через `new` где-то в коде. Объекты перечисления создаются самой JVM один раз при загрузке класса в память.

### 2. Откуда берутся методы? (Секрет компилятора)

У `enum` есть базовые методы: `name()` (возвращает имя константы строкой) и `ordinal()` (возвращает порядковый номер, начиная с 0). Они приходят из родительского класса `java.lang.Enum`.

Но есть два метода, о которых часто спрашивают: `values()` и `valueOf(String)`. **Их нет в классе `Enum`!** Их заботливо генерирует и добавляет в твой класс сам компилятор на этапе сборки.

- `values()` — возвращает массив всех констант.
- `valueOf("NEW")` — ищет константу по точному совпадению имени (и бросает `IllegalArgumentException`, если не найдет).

### 3. Суперсилы Enum (Для уровня Middle/Senior)

Вот что реально хотят услышать на собеседовании, когда просят "рассказать про `enum`":

**Суперсила 1: Состояние и поведение** — Так как это полноценный класс, ты можешь добавлять в него свои поля, писать кастомные конструкторы и методы.

```java
public enum ErrorCode {
    NOT_FOUND(404, "Ресурс не найден"),
    SERVER_ERROR(500, "Ошибка сервера");

    private final int code;
    private final String message;

    ErrorCode(int code, String message) { // Конструктор неявно private
        this.code = code;
        this.message = message;
    }
    // Геттеры...
}
```

**Суперсила 2: Полиморфизм констант (Паттерн Стратегия/Состояние)** — Ты можешь заставить каждую константу реализовать один и тот же метод по-своему! Это избавляет код от огромных простыней `switch-case` или `if-else`.

```java
public enum Operation {
    PLUS {
        public int apply(int x, int y) { return x + y; }
    },
    MINUS {
        public int apply(int x, int y) { return x - y; }
    };

    public abstract int apply(int x, int y); // Абстрактный метод внутри enum!
}
```

**Суперсила 3: Идеальный Singleton (Совет от Джошуа Блоха)** — На собеседованиях по паттернам часто просят написать потокобезопасный `Singleton`. Самый пуленепробиваемый способ в Java — это `enum` из одного элемента. Почему?

1. JVM сама гарантирует потокобезопасность при инициализации.
2. Его невозможно сломать через Рефлексию (Reflection API).
3. Он абсолютно безопасен при сериализации/десериализации (стандартные синглтоны ломаются и создают новые объекты при десериализации, а `enum` — нет).

**Суперсила 4: Высокопроизводительные коллекции** — Если тебе нужно хранить набор `enum` или использовать их как ключи в мапе, всегда используй `EnumSet` и `EnumMap` вместо обычных `HashSet` и `HashMap`. Под капотом они реализованы через битовые векторы (Bit Vectors). Это работает с невероятной, "железной" скоростью и занимает минимум памяти (нет никаких хэшей, корзин и коллизий).

## Модификаторы доступа

В Java их всего четыре. Они определяют, кто и откуда может видеть твои классы, переменные, методы и конструкторы.

### 1. Классическая шпаргалка (Матрица видимости)

Для начала зафиксируем сухую базу:

| **Модификатор** | **Внутри класса** | **В том же пакете** | **В классе-наследнике (другой пакет)** | **Везде (глобально)** |
|---|---|---|---|---|
| **`private`** | ✅ Да | ❌ Нет | ❌ Нет | ❌ Нет |
| **`default` (без слова)** | ✅ Да | ✅ Да | ❌ Нет | ❌ Нет |
| **`protected`** | ✅ Да | ✅ Да | ✅ Да | ❌ Нет |
| **`public`** | ✅ Да | ✅ Да | ✅ Да | ✅ Да |

А теперь давай разберем каждый из них через призму ловушек на собеседованиях и реальной архитектуры.

### 2. `private` — Твоя крепость

Самый строгий модификатор. Виден только внутри того класса, где объявлен.

- **Архитектурное правило:** Все поля класса **всегда** должны быть `private`. Доступ к ним должен осуществляться только через методы (геттеры/сеттеры) или бизнес-методы. Это основа инкапсуляции.
- **Секретный прием:** Конструктор тоже может быть `private`. Мы уже обсуждали это в теме `Enum` и паттерне `Singleton`. Также приватные конструкторы используют в утилитных классах (например, `Math`), чтобы никто не мог сделать `new Math()`.

### 3. `default` (Package-Private) — Командный игрок

Если ты не написал никакого модификатора, Java применяет `default`. Элемент будет виден **только внутри того же пакета**.

- **Где это ловушка:** Многие новички думают, что если не написать модификатор, то это равносильно `public` или что это "просто так".
- **Архитектурная ценность:** Это невероятно мощный инструмент для построения чистой архитектуры и Domain-Driven Design. Ты можешь создать в пакете 10 классов, которые общаются между собой, но сделать `public` только один фасадный класс. Остальные 9 классов будут `package-private`. Никто из других слоев приложения (например, из контроллеров) физически не сможет вызвать их напрямую и сломать логику.

### 4. `protected` — Наследственный фактор

Виден внутри своего пакета **И** во всех классах-наследниках, даже если они лежат в других пакетах.

- **Любимый вопрос на засыпку:** _"Я создал класс `Parent` в пакете А с `protected` методом. В пакете Б я создал класс `Child extends Parent`. Могу ли я в пакете Б создать объект `Parent p = new Parent();` и вызвать у него этот метод?"_
- **Правильный ответ:** НЕТ! Ты не сможешь вызвать `p.method()`. Модификатор `protected` дает доступ к методу только **через наследование** (внутри методов самого `Child`), а не через ссылку на экземпляр родительского класса в другом пакете. На этом сыплются очень многие.

### 5. `public` — Открытая дверь

Виден абсолютно везде.

- **Архитектурное правило:** `public` должно быть как можно меньше. Делай публичными только те методы, которые составляют API твоего класса — то есть его контракт, то, что он обещает делать для других компонентов системы. Чем шире публичный API, тем сложнее потом поддерживать и рефакторить код, потому что на него могут быть завязаны сотни других классов.

## Modern Java Basics

### 1. Вывод типов локальных переменных: `var` (Java 10)

Многие новички, приходящие из JavaScript или Python, радуются `var`, думая, что Java стала динамически типизированной. Это главная ловушка на собеседовании.

- **Как это работает:** `var` — это синтаксический сахар для компилятора. Java остается строго типизированной. Просто компилятор сам догадывается о типе переменной по тому значению, которое ты ей присваиваешь справа от знака равно.
    - _Было:_ `Map<String, List<User>> map = new HashMap<>();`
    - _Стало:_ `var map = new HashMap<String, List<User>>();`
- **Где можно использовать:** **Только для локальных переменных** внутри методов, в циклах `for` и `try-with-resources`.
- **Где НЕЛЬЗЯ использовать (ошибки компиляции):**
    - Для полей класса (потому что тип поля должен быть известен до создания объекта).
    - В параметрах методов и возвращаемых типах.
    - Нельзя написать `var x;` без инициализации (компилятору не за что зацепиться, чтобы понять тип).
    - Нельзя присвоить `null`: `var str = null;` (тип `null` не определен).

### 2. Records: Убийца Lombok (Java 14/16)

Это, пожалуй, самое важное архитектурное нововведение для работы с данными. `record` — это специальный вид класса, созданный для одной цели: быть прозрачным и неизменяемым носителем данных (DTO, сообщения для брокеров вроде Kafka, ответы API).

- **Как это работает:** Ты пишешь всего одну строчку: `public record UserDto(Long id, String name) {}`
- **Что делает компилятор под капотом:**
    1. Создает класс `final` (от него нельзя наследоваться).
    2. Делает все поля `private final` (они неизменяемые).
    3. Генерирует конструктор со всеми аргументами.
    4. Автоматически создает идеальные `equals()`, `hashCode()` и `toString()`.
    5. Создает геттеры, но **без префикса get** (методы называются просто `id()` и `name()`).
- **Ловушки на собеседовании:**
    - _"Может ли record наследоваться от другого класса?"_ — **Нет**, так как он уже неявно наследуется от `java.lang.Record`.
    - _"Может ли реализовывать интерфейсы?"_ — **Да**, сколько угодно.
    - _"Можно ли добавить валидацию?"_ — **Да**, через "компактный конструктор" (без указания аргументов), где можно проверить данные (например, `if (id < 0) throw ...`) перед тем, как они запишутся в поля.

### 3. Switch Expressions и Pattern Matching (Java 12 - 21)

Старый `switch-case` с его вечными `break` был источником тысяч багов (забыл `break` — логика "провалилась" в следующий `case`). Современная Java полностью переосмыслила этот оператор.

- **Новый синтаксис (Стрелочный `switch`):** Вместо двоеточия используется стрелка `->`. Главный плюс — **нет эффекта проваливания (fall-through)**. Отрабатывает только один блок, и `break` больше писать не нужно.
- **Switch как выражение (Expression):** Теперь `switch` может **возвращать значение** прямо в переменную.

    ```java
    String type = switch (day) {
        case MONDAY, FRIDAY -> "Рабочий";
        case SATURDAY, SUNDAY -> "Выходной";
        default -> "Неизвестно";
    };
    ```

- **Ключевое слово `yield`:** Если логика внутри `case` сложная и занимает несколько строк (нужны фигурные скобки `{}`), то для возврата значения из этого блока используется новое слово `yield` (вместо `return`).
- **Pattern Matching для `instanceof` (Java 16):** Раньше мы писали так: `if (obj instanceof String) { String s = (String) obj; s.length(); }`. Теперь приведение типов происходит автоматически прямо в условии: `if (obj instanceof String s) { s.length(); }`.
- **Pattern Matching для `switch` (Java 21):** Теперь в `switch` можно передавать не только числа, строки и Enum, но и **любые объекты**, проверяя их типы:

    ```java
    return switch (obj) {
        case String s -> "Строка: " + s;
        case Integer i -> "Число: " + i;
        case UserDto u -> "Пользователь: " + u.name();
        default -> "Что-то другое";
    };
    ```

### 4. Sealed Classes (Запечатанные классы) (Java 17)

До появления `sealed` у нас было только две крайности: либо класс открыт для наследования всем подряд (обычный класс), либо закрыт для всех абсолютно (модификатор `final`). `sealed` классы дают нам золотую середину: мы можем разрешить наследование, но **только строго определенному списку классов**.

**Как это работает:** Ты объявляешь класс или интерфейс с ключевым словом `sealed` и через ключевое слово `permits` явно перечисляешь, кто имеет право от него наследоваться.

```java
public sealed interface PaymentResult permits Success, Error, Pending {
}

// Эти классы могут быть обычными классами или record'ами
public record Success(String receiptId) implements PaymentResult {}
public record Error(String errorMessage) implements PaymentResult {}
public record Pending(String transactionId) implements PaymentResult {}
```

**Зачем это нужно (Архитектурная ценность):** Это инструмент для Domain-Driven Design (DDD). Когда ты пишешь ядро бизнес-логики (например, модуль оплат), ты хочешь гарантировать, что результат оплаты может быть только трех видов: Успех, Ошибка или Ожидание. И ты физически запрещаешь другим разработчикам в других пакетах создать свой класс `class Timeout implements PaymentResult`, который сломает твою логику обработки.

**Жесткие правила (Ловушки на собеседовании):** Интервьюер спросит: _"Какие правила обязаны соблюдать классы-наследники запечатанного класса?"_ Их три, и их нужно знать наизусть:

1. **Знание при компиляции:** Все разрешенные классы (указанные в `permits`) должны быть известны компилятору и лежать в том же модуле (или пакете).
2. **Прямое наследование:** Наследник обязан напрямую расширять (extends) или реализовывать (implements) `sealed` класс.
3. **Обязательный модификатор наследника:** Каждый разрешенный класс-наследник **обязан** выбрать свою дальнейшую судьбу, указав один из трех модификаторов:
    - `final` — иерархия закрывается навсегда (дальше наследоваться нельзя). Эту роль отлично выполняют `record`, так как они `final` по умолчанию.
    - `sealed` — наследник тоже становится запечатанным и должен перечислить уже своих разрешенных потомков через `permits`.
    - `non-sealed` — (пишется через дефис!) наследник заново открывает иерархию для всего остального мира, разрешая наследоваться от себя кому угодно.

**Секретное комбо для сеньора: Sealed + Switch Pattern Matching** — Главная суперсила `sealed` классов раскрывается в паре с новым `switch`. Если ты прогоняешь `sealed` тип через `switch`, компилятор **знает все возможные варианты наследников**. Это значит, что тебе **больше не нужно писать блок `default`**!

```java
PaymentResult result = ...;

// Компилятор видит, что мы перебрали все 3 разрешенных варианта.
// Блок default не нужен!
String message = switch (result) {
    case Success s -> "Оплачено: " + s.receiptId();
    case Error e -> "Ошибка: " + e.errorMessage();
    case Pending p -> "В обработке: " + p.transactionId();
};
```

_В чем профит:_ Если завтра кто-то добавит новый статус `Refunded` в `permits`, код не скомпилируется, пока ты не добавишь обработку этого нового кейса в `switch`. Никаких скрытых багов в рантайме!
