# Строки

Как устроен `String`, чем от него отличаются `StringBuilder` и `StringBuffer`, что такое String Pool и `intern()`. Чаще всего спрашивают, почему `String` неизменяемый, что вернёт `==` для строк и нужен ли `StringBuilder` для `a + b + c`.

## String и его родственники { #string-family }

### Почему `String` неизменяемый? { #string-immutable }

**Уровень:** Junior

!!! abstract "Ответ вслух"
    После создания строку нельзя изменить: `replace()`, `toUpperCase()` и конкатенация возвращают новый объект. Это нужно для безопасности (строки — ключи `HashMap`, пароли, пути), потокобезопасности и String Pool. Обратная сторона — склейка строк в цикле создаёт кучу мусора.

Объекты класса `String` неизменяемы (immutable): после создания строки её содержимое поменять нельзя. Вся суть различий между `String`, `StringBuilder` и `StringBuffer` сводится к двум понятиям — **изменяемость (mutability)** и **потокобезопасность (thread safety)**.

- **Как это работает:** при конкатенации `String s = "Hello" + " World";` или вызове `s.replace()`, `s.toUpperCase()` исходная строка **не меняется**. В куче создаётся **новый** объект, а старый, если на него больше нет ссылок, достаётся сборщику мусора.
- **Зачем так сделали:**
    1. **Безопасность:** строки — ключи в `HashMap`, пароли, пути к файлам и URL. Если бы строку можно было изменить из другого места программы, это открыло бы дыры в безопасности.
    2. **Потокобезопасность:** неизменяемый объект можно передавать между потоками без гонок (race conditions).
    3. **Кэширование:** неизменяемость сделала возможным [String Pool](#string-pool).

```java
String s = "hello";
s.toUpperCase();                // ❌ результат потерян: s по-прежнему "hello"
String upper = s.toUpperCase(); // ✅ новый объект "HELLO"
```

!!! warning "Ловушка: конкатенация в цикле"
    Если склеивать тысячи строк через `+` в цикле, на каждой итерации создаётся новая строка с копией всего накопленного текста. Это тысячи промежуточных объектов и O(n²) копирования — для такой работы есть [`StringBuilder`](#stringbuilder).

### Чем `StringBuilder` отличается от `StringBuffer`? { #stringbuilder }

**Уровень:** Junior

!!! abstract "Ответ вслух"
    Оба изменяемые: дописывают символы во внутренний массив, а не создают новую строку на каждую операцию. `StringBuffer` синхронизирован и поэтому медленнее, `StringBuilder` — нет. В современном коде почти всегда нужен `StringBuilder`.

#### `StringBuilder` — изменяемый, без синхронизации { #stringbuilder-impl }

Создан, чтобы решить проблему производительности `String`.

- **Как это работает:** внутри — расширяемый массив (`byte[]` с Java 9). `append()` не создаёт новый объект, а дописывает символы в этот массив. Если массив заполнился, создаётся новый — вдвое больше плюс 2 — и данные копируются.
- **Где применять:** везде, где текст собирается динамически — форматирование документов, разбор больших файлов, генерация сложных SQL-запросов.
- **Нюанс:** **не потокобезопасен**. Если два потока одновременно сделают `append()`, данные перемешаются или вылетит `ArrayIndexOutOfBoundsException`.

#### `StringBuffer` — изменяемый, синхронизированный { #stringbuffer }

Близнец `StringBuilder` с одним отличием.

- **Как это работает:** основные методы (`append`, `insert`, `delete`) помечены `synchronized`, поэтому строку в каждый момент меняет только один поток.
- **Где применять:** практически **нигде** в современном коде.
- **Почему устарел:** синхронизация замедляет каждый вызов, а несколько потоков, дописывающих в одну строку, на практике почти не встречаются. Обычно каждый поток собирает свою строку в `StringBuilder` и передаёт дальше готовый `String`.

```java
StringBuilder sb = new StringBuilder();
for (String part : parts) {
    sb.append(part).append(", "); // дописывает во внутренний массив, новых строк не создаёт
}
String result = sb.toString();     // одна итоговая строка
```

| **Характеристика** | **String** | **StringBuilder** | **StringBuffer** |
|---|---|---|---|
| **Изменяемость** | Нет (immutable) | Да (mutable) | Да (mutable) |
| **Потокобезопасность** | Да (из-за неизменяемости) | Нет | Да (через `synchronized`) |
| **Производительность** | Медленно при склеивании | **Быстро** | Медленнее из-за блокировок |
| **Когда использовать** | Хранение текста, ключи `Map` | Сборка текста в одном потоке | Только легаси-код |

!!! warning "Ловушка: «StringBuffer — для многопоточного кода»"
    Синхронизирован только каждый отдельный вызов. Последовательность «проверил длину → дописал» из двух потоков всё равно может перемешаться. Собирай строку локально в `StringBuilder`, а между потоками передавай готовый `String`.

### Нужен ли `StringBuilder` для `a + b + c`? { #concat-indy }

**Уровень:** Senior

!!! abstract "Ответ вслух"
    Вне цикла — нет. С Java 9 оператор `+` компилируется не в `StringBuilder`, а в `invokedynamic` с `StringConcatFactory`, и JVM сама выбирает оптимальную стратегию склейки. А вот внутри цикла `StringBuilder` по-прежнему обязателен.

Интервьюеры любят спросить: _"Если я пишу `String s = a + b + c;` вне цикла, обязательно ли переписывать на `StringBuilder`?"_

**Ответ:** нет. До Java 8 включительно компилятор сам превращал `+` в цепочку `StringBuilder.append()`. Начиная с Java 9 ([JEP 280](https://openjdk.org/jeps/280)) используется `StringConcatFactory` с инструкцией `invokedynamic`: JVM на лету решает, как склеить строки, и выделяет ровно столько памяти, сколько нужно.

Поэтому для простых склеиваний вне циклов `+` работает не хуже и читается лучше. **Внутри циклов** `StringBuilder` всё ещё обязателен: оптимизация действует в пределах одного выражения.

```java
String s = a + b + c;  // ✅ одна инструкция invokedynamic — StringBuilder руками не нужен

String result = "";
for (String part : parts) {
    result += part;    // ❌ новая строка на каждой итерации — O(n²) копирования
}
```

Проверить, во что скомпилировалась конкатенация, можно дизассемблером `javap`: в Java 9+ вместо вызовов `StringBuilder` там будет `invokedynamic` с `makeConcatWithConstants`.

```bash
javap -c Main.class | grep -E "invokedynamic|StringBuilder"
```

!!! warning "Ловушка: «компилятор и цикл оптимизирует»"
    `invokedynamic` склеивает части одного выражения. Каждая итерация `result += part` — отдельное выражение с новой строкой, поэтому в цикле копирование растёт квадратично.

## String Pool { #pool }

### Что такое String Pool? { #string-pool }

**Уровень:** Junior

!!! abstract "Ответ вслух"
    Это область в куче, где хранится по одному экземпляру каждой строки-литерала. Два литерала `"Java"` указывают на один объект, поэтому `==` для них даёт `true`. `new String("Java")` всегда создаёт новый объект в обычной куче, и `==` с литералом даст `false`.

Строки используются повсюду (текст, ключи, пути, настройки) и занимают значительную часть памяти. Чтобы не плодить тысячи одинаковых объектов `"User"` или `"Error"`, в Java есть механизм кэширования — **String Pool**.

Это специальная область памяти внутри кучи. Её задача — хранить **только один экземпляр** каждой уникальной строки, созданной через литерал (в двойных кавычках).

- **Создание через литерал:** при `String s1 = "Java";` JVM проверяет пул: есть ли уже строка «Java»?
    - Если **нет** — создаёт объект в пуле и возвращает ссылку на него.
    - Если **есть** (например, строчкой ниже `String s2 = "Java";`) — **не создаёт** новый объект, а возвращает ссылку на существующий.
    - **Итог:** `s1 == s2` вернёт `true` — обе переменные указывают на один объект.

Любимый вопрос на скринингах — что будет, если создать строку через `new`:

```java
String s1 = "Java";               // идёт в пул
String s2 = new String("Java");   // создаёт новый объект в обычной куче
String s3 = "Ja" + "va";          // константы склеиваются при компиляции → тот же литерал из пула

System.out.println(s1 == s2);      // false: разные объекты
System.out.println(s1 == s3);      // true: оба — литерал "Java" из пула
System.out.println(s1.equals(s2)); // true: содержимое одинаковое
```

С `new` ты **принудительно** говоришь JVM: «создай новый объект в куче, даже если такая строка уже есть в пуле». Поэтому `s1 == s2` — `false`: `s1` смотрит в пул, `s2` — в обычную кучу.

!!! note "Золотое правило"
    Никогда не создавай строки через `new String("text")` без очень специфической причины. Это пустая трата памяти.

!!! warning "Ловушка: сравнивать строки через `==`"
    `==` сравнивает ссылки, и с литералами он «случайно» работает, а со строками из файла, БД или `new` — нет. Сравнивай строки только через `equals()`.

### Как работает `intern()`? { #intern }

**Уровень:** Middle

!!! abstract "Ответ вслух"
    `intern()` ищет строку с таким же содержимым в String Pool: если нашёл — возвращает ссылку из пула, если нет — кладёт строку туда и возвращает её. Это позволяет дедуплицировать строки, пришедшие из файла или БД. До Java 7 пул жил в PermGen и при активном `intern()` падал с `OutOfMemoryError: PermGen space`, с Java 7 он в куче и чистится GC.

Что делать, если строка пришла динамически (прочитали из файла, из БД или склеили через `StringBuilder`), а мы хотим положить её в пул ради экономии памяти? Для этого есть `intern()`:

- Если строка с таким содержимым в пуле **уже есть** — метод возвращает ссылку на объект из пула. Исходный динамический объект со временем соберёт GC.
- Если **нет** — JVM добавляет эту строку в пул и возвращает ссылку на неё.

```java
String s1 = "Hello";
String s2 = new String("Hello");
String s3 = s2.intern();

System.out.println(s1 == s2); // false (один в пуле, другой в куче)
System.out.println(s1 == s3); // true (s3 получил ссылку из пула, где уже лежал s1)
```

#### Историческая справка { #intern-history }

Если на собесе заговорят об «опасности» `intern()`:

- **До Java 7:** String Pool находился в PermGen, у которого был фиксированный размер и который почти не очищался. При активном использовании `intern()` память быстро забивалась, и приложение падало с `OutOfMemoryError: PermGen space`.
- **С Java 7:** пул перенесли в основную кучу, и GC умеет удалять из него строки, на которые больше нет ссылок. А с Java 8 PermGen и вовсе заменили на [Metaspace](jvm.md#metaspace).

!!! warning "Ловушка: `intern()` не бесплатен"
    Риска `PermGen space` больше нет, но пул — это хэш-таблица внутри JVM, и каждый `intern()` — поиск в ней. Интернировать миллионы уникальных строк ради экономии памяти бессмысленно: выигрыш есть, только когда одинаковых строк много.

## Шпаргалка { #cheatsheet }

| Тема | Запомнить |
|---|---|
| **Неизменяемость `String`** | Любая «модификация» создаёт новый объект; причины — безопасность, потоки, String Pool |
| **`StringBuilder`** | Изменяемый, без синхронизации, массив растёт вдвое + 2 — выбор по умолчанию для сборки текста |
| **`StringBuffer`** | То же, но `synchronized` — только легаси |
| **`a + b + c`** | С Java 9 — `invokedynamic` + `StringConcatFactory`; в цикле всё равно `StringBuilder` |
| **String Pool** | Один экземпляр каждого литерала, в куче с Java 7; `new String()` пул обходит |
| **`==` для строк** | Сравнивает ссылки; содержимое — только через `equals()` |
| **`intern()`** | Вернуть строку из пула или положить её туда; полезен, когда одинаковых строк много |
